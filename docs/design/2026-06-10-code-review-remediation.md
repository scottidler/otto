## Problem Statement

### Background

The 2026-06-10 review examined all of src/ (cfg, cli, executor, executor/state, ports, makefile, tui, app/main/utils), the test suite, docs/, CI, and repo hygiene, validated against the user rules (logging, CLI conventions, naming, test placement, no-dead-code) and the four docs/design/ documents. Empirical confirmations include: shell injection via env values (a probe value created a file on disk), bare `otto` running the Clean builtin instead of user tasks, typo'd task names exiting 0, dependency cycles exiting 0 with zero output, `--keep-last` deleting the newest runs in filesystem mode, `otto clean` following a symlink and deleting a directory outside `~/.otto`, the v1-to-v2 migration crash window bricking the DB ("duplicate column name"), `nargs: "0:5"` panicking the config loader, multibyte-whitespace dedent panicking, `$(shell ...)` and `$(VAR)` surviving Makefile conversion and breaking at runtime, invalid UTF-8 truncating captured task output while the task "succeeds", six different cache filenames for the same script across six runs, a spawn failure being reported as a task named "such" and then hanging the scheduler, `otto Upgrade` dying on ETXTBSY, `-j 0` hanging forever, and main-branch CI red for 15 consecutive runs over 3+ months.

**2026-08-29: every one of those empirical confirmations was re-run and every one still reproduces**, with three descriptions corrected (cycles now print skip lines but still exit 0; `-j 0` is a 99.3%-CPU hot spin rather than a block; `otto Upgrade` fails before ETXTBSY is reachable).

Positive findings worth recording: drain-on-failure works exactly as the conditional-deps design promises (failing task drains parallel work, `when: failure` fixer and `when: always` cleanup both fire, exit stays 1); no SQL injection exists anywhere (every user value is bound via `params![]`); the concurrent stdout/stderr drain design avoids the classic pipe-buffer deadlock (verified at 4 MB of output); the ports layer is honest DI; cfg/edge.rs is a model file; the ParamSpec round-trip shipped exactly as its design doc records; `apply_cwd_flag` and log rotation in main.rs are careful and well tested; auto-prune runs even on failed runs with the rationale recorded; install.sh verifies checksums; version discipline (Cargo.toml == latest tag, GIT_DESCRIBE) is correct; and `.otto.yml` genuinely dogfoods the flagship features.

**2026-08-29 additions to the positive list.** The v1.3.0 features were probed for the defect classes in this doc and came back clean on every axis except escaping: `foreach: command:` and `choices-command` both fail loudly with exit 1 rather than silently producing an empty list; neither executes at `--help` time (`other --help` renders `[dynamic choices: <command>]` without running it, and an execution counter confirmed zero extra runs); `tty: true` serializes correctly at `-j 1` and at default `-j`; `--tasks` honors `-o` and emits JSON when piped. `DynamicResolver` memoizes per invocation in a `RefCell<HashMap<..>>` (`resolver.rs:44-54`) and deliberately does not cache failures.

### Problem

Six systemic defect classes, plus per-module bugs. **All six still hold on 2026-08-29**; class 6 has gotten measurably worse.

1. **Silent success on broken input, the worst failure mode a task runner can have.** A typo'd task name exits 0 having run nothing; a dependency cycle exits 0; a top-level `task:` typo used to parse to zero tasks (**closed by v1.4.0**); bare `otto` with default `tasks: ["*"]` expands the injected builtins and runs `Clean` instead of the user's tasks; `otto: tasks: []` plus an explicit task request prints nothing and exits 0; the Makefile converter silently corrupts continuations, pattern rules, `export`, and target-specific variables into plausible-looking garbage; foreach with up-to-date subtasks silently kills everything downstream. **New instance:** six `otto:` keys (`jobs`, `home`, `verbosity`, `name`, `version`, `about`) are accepted, ignored, documented as working behavior in `docs/commands/ottofile-reference.md:39-42`, and now *guaranteed* to parse by `deny_unknown_fields`. Strict parsing made accepted-and-ignored keys look official.
2. **Two backends, two behaviors.** The DB and filesystem-fallback paths of `clean` disagree: `--keep-last` is inverted in fs mode, `--keep-failed` is silently ignored, `--project-filter` is substring-match in one and exact-hash in the other, and the DB path reconstructs run directories as `otto-<hash>` while workspaces are actually `<name>-<hash>`. **Measured against the live `~/.otto`: 222 project directories, of which 2 begin with `otto-`.** The same `otto-` prefix assumption appears a third time in `pruning.rs:90`, so cache pruning also sees 2 of 222. TUI and terminal paths diverge. Mem and Real port impls diverge on UTF-8, missing-file removal, and canonicalize, and duplicate the retention policy line-for-line.
3. **State and persistence integrity.** The v1-to-v2 migration runs ALTER and set_version as separate non-transactional steps; a crash between them bricks the DB forever, and `StateManager::try_new()` is `.ok()` with zero logging. `runs.timestamp` carries a global UNIQUE in seconds. `record_run_complete_in_db` has zero production callers: **its only two references in the entire tree are its definition and its own unit test**, so every run is perpetually "running". The recorded exit code is always 1. No busy_timeout, and zero `spawn_blocking` anywhere. Plain `fs::write` plus a write-only-if-absent script cache means a torn write permanently poisons an executable script. The script hash itself is nondeterministic.
4. **Strings where types belong.** The scheduler extracts the failed task's name by parsing the error string (`split_whitespace().nth(1)`, so a spawn failure becomes task "such" and the run hangs); the exit code travels through `{:?}` formatting and back; early `?` exits inside spawned task bodies bypass the completion channel and JoinHandles are never awaited; `env_to_json` corrupts multiline values; eyre chains are flattened in main.rs. **STAYS: NOT covered by `2026-08-29-strict-ottofile-schema.md`** (named a Non-Goal there; it remains remediation scope).
5. **Containment and injection.** Env values and CLI params are templated raw into generated bash/python scripts; command-substitution output is re-expanded as variable references; a bare `$VAR` is silently left unresolved when `${VAR}` appears in the same string; `clean` follows symlinks under `~/.otto` and `remove_dir_all`s targets outside it; `otto Upgrade` does no integrity verification and cannot complete an install anyway. **The class grew in v1.3.0**: `foreach: command:` and `choices-command` add two fresh sources of externally-shaped text feeding the same unescaped generator, plus a path-traversal vector through foreach item names.
6. **The repo's own gates lie, and one of them does not exist.** Main-branch `CI` is still red, now at 5 failures rather than 4, one of them shipped by v1.4.0 itself. `Release` never consults `CI`, so the red has never blocked a publish. The three steps of the CI `test` job run sequentially in one job, so the test failure means `cargo fmt --check` and `cargo clippy` have not actually executed on main in months, and any drift they would catch is invisible rather than merely tolerated. `Cargo.lock` is still gitignored for a binary crate whose pre-commit hooks run `--locked`. The GH workflow's clippy is still bare `cargo clippy -- -D warnings` against `--all-targets --all-features` everywhere else, and its steps are sequential fail-fast so the test failure still hides fmt and clippy. A phantom tracing/tracing-subscriber logging stack is still declared and never referenced. 13 `debug!` calls cover 638 production functions against an always-on entry-DEBUG rule, with `executor/action.rs`, `executor/state/manager.rs`, `makefile/parser.rs`, and `ports/http.rs` at zero and `scheduler.rs` holding 33 of the 48 total. docs/ still mixes evergreen references with ~20 stale one-off plans including two that document a removed nom parser, and v1.4.0 added two more files to that directory rather than pruning it. Real Tatari service Makefiles are still committed in this repo, which `gh repo view` confirms is `PUBLIC`.

### Goals

- Fix all 15 criticals with regression tests in the same change.
- Eliminate the six systemic classes, not just their instances.
- Make every doc (design docs, README, converter doc, code comments, `.cursor/rules`) tell the truth: implement the claim or amend the doc, never leave the contradiction.
- Bring rule-drift up to the user's own rules (CLI case-insensitivity, no RUST_LOG, no `dirs::data_local_dir()`, tests in sibling files, no `#[allow(dead_code)]`, entry-DEBUG logging, file-size caps).

## Architecture and Product Assessment

The phased plan below is tactical. This section is the altitude view: whether the architecture is the right shape, and whether otto-the-product is worth the investment the plan represents. **Re-checked 2026-08-29; the assessment stands, with the drift noted inline.**

### What otto is

A declarative YAML task runner positioned as a make replacement: DAG dependencies (`before`/`after`), parallel-by-default execution (`-j`), conditional edges (`when: success|failure|always` plus `on-failure:` sugar) with drain-on-failure, foreach fan-out (glob/items/range/**command**, serial or parallel, with aggregating virtual parents), file dependencies (`input`/`output` up-to-date skipping), per-task typed CLI params that become real clap subcommands with help/choices/**dynamic choices**/defaults, env evaluation with command substitution, file-based data passing between tasks, sqlite-backed run history with History/Stats/Clean builtins, a TUI dashboard, a Makefile converter, self-upgrade, **a machine-readable `--tasks` surface, `tty: true` for tasks needing the terminal, and `--no-prefix`**: shipped as a single static binary with install.sh, Docker, and a GitHub Action.

### Positioning

Otto sits in a real gap between the command launchers (just, go-task) and the artifact-correct build systems (bazel, earthly). The thesis is effectively **CI semantics on your laptop**: a DAG with conditional flow, observable history, and per-task CLI ergonomics. Four features are genuinely distinctive and no near-peer has the combination:

1. **Params as real subcommands.**
2. **Multiple tasks per invocation, each with its own args.**
3. **Conditional dependencies with drain-on-failure.**
4. **Run history and stats.**

A fifth is now arguably in that set: **dynamic fan-out and dynamic choices from a command**, which is what made otto a plausible replacement for a hand-rolled generator in a consumer repo. It is also the feature that most needs Phase 3's escaping work before it can be recommended.

One deliberate scope boundary worth stating: otto is task-oriented, not artifact-oriented. File deps are a freshness check, not make's incremental-build model. That is the right call for the niche, but the Makefile converter implies a parity the model does not have, which is part of why Phase 7 makes it diagnose loudly what it cannot express.

### Architectural strengths

- **The layering direction is right.** cfg -> cli -> executor -> state, with data flowing one way.
- **The ports layer is honest hexagonal architecture**, with one correction: `ports/http.rs` is now entirely dead (see Phase 5/9). The fs and db ports remain genuinely exercised.
- **The execution core has the right shape**: an event-driven scheduler over bounded channels, semaphore-bounded parallelism, concurrent pipe drains, and a single `classify_edge` source of truth. v1.3.0's serial-foreach redesign (ordering as a scheduler property via `SerialGroups`, `scheduler.rs:208-278`, replacing chain `before:` edges) is a strict improvement to that shape and vindicates it.
- **Style-preserving round-trip config serialization** is unusually sophisticated for a tool this size.
- **Workspace-per-run plus a content-addressed script cache** is a good persistence design once Phase 3 makes the hashing deterministic and the writes atomic.
- **The distribution posture matches the niche**, with the caveat that the self-upgrade leg of it is currently non-functional.
- **The strict-schema work is the model for the rest of this plan.** One reproduced defect, one small doc, fail-closed by construction, error messages naming field and path and line, a published key reference, and a drift test that fails when the schema and the reference disagree. That is what "eliminate the class, not the instance" looks like when it lands.

### Architectural liabilities

These are structural, beyond the per-site bugs the phases fix.

1. **parser.rs is a god module,** and it grew: 3457 lines at review time, **4091 today**. Phase 9 decomposes it, but the deeper fix is a staged compilation pipeline: parse args -> load config -> expand/propagate -> plan, with typed artifacts between stages. That was the missing sibling doc's core proposal.
2. **Builtins are phantom tasks,** injected into the user's namespace then filtered or intercepted at three layers. Root cause of two criticals. Now also the reason `Convert` and `Upgrade` are unreachable behind any global flag while `Clean`/`Graph`/`History`/`Stats` work: the difference is simply which ones got hand-written handlers in `app.rs:296-313`.
3. **Token-equality partitioning is inherently ambiguous.** Phase 8's lookahead fixes the common case; the `=`-form escape hatch must stay documented.
4. **Presentation forks above the scheduler instead of below it.** Partially improved: `is_virtual_parent` no longer drifts, because both paths now route through `impl From<parser::Task> for Task` (`executor/task.rs:249`, `121f384`). The ~40 lines of duplicated setup and the builtin divergence remain.
5. **Three "Task" types with lossy conversions** (`cfg::TaskSpec`, `parser::Task`, `executor::Task`).
6. **Stringly-typed seams.** eyre string errors at every module boundary are why the scheduler parses task names out of error messages.
7. **Config loading executes code.** `$()` runs at load time. v1.3.0 was careful here (neither `foreach: command:` nor `choices-command` runs at `--help` time, verified), which makes the *existing* eager `$()` evaluation the odd one out. Document the posture (Phase 10); lazy evaluation is the structural fix.
8. **The state layer mixes storage with disk lifecycle.** `StateManager` performing `remove_dir_all` is a layering violation that helped the wrong-dirname bug hide, and it means the symlink-deletion hole has to be patched in two places.

### Product utility gaps

Not bugs: missing or questionable surface, judged against the "CI semantics locally" thesis. **Re-checked 2026-08-29.**

- **No plan/dry-run output for tasks.** `--tasks` (v1.3.0) delivers the machine-readable task list, which was the near-term half. "What would run, in what order, and why" is still absent. (`dry_run` in app.rs is the Clean builtin's flag, not a scheduler plan.) Strongest candidate for the next feature doc, and it was the missing sibling doc's headline.
- **No timeouts anywhere.** Still zero: no `timeout:` task key, no global ceiling. Two `.cursor/rules` files document a `timeout:` key that has never existed.
- **No shell completions.** `clap_complete` is not a dependency. No watch mode.
- **The README improved but is still thin.** 121 lines now, up from 62. The false build-time version-mismatch claim is still there at `README.md:121` against a 23-line `build.rs` that only sets `GIT_DESCRIBE`.
- **The TUI is the least essential surface and the least finished.** Unchanged: dead Ctrl+C, ignored builtins, incoherent scrolling, width-0 hang.
- **The Makefile converter's strategic value is onboarding, and in its current state it harms onboarding.** `src/makefile/` has gained exactly one line since 2025-11-06.
- **The differentiating feature is still the least trustworthy one.** Run history/stats is otto's unique selling point, and every defect this doc found there is untouched: runs never marked complete, exit codes always 1, concurrent runs vanishing, clean deleting the wrong things or nothing. Phase 4 is product-critical, not hygiene.

### Verdict

The architecture is the right shape with two structural exceptions (the parser god-module and builtins-as-phantom-tasks), and the execution core's design decisions are sound and in several places better than the tool's weight class. The product occupies a real niche with four, arguably five, genuinely distinctive features. The gap is trust: the silent-success class lands precisely on the features that differentiate otto, so the tool is most dangerous exactly where it is most interesting.

**2026-08-29 amendment.** Two and a half months of evidence sharpen this. v1.3.0 and v1.4.0 demonstrate the team can ship small, reproduced, fail-closed fixes with drift tests, which is the exact competence this plan needs. They also demonstrate the failure mode this plan exists to stop: shipping onto an unverified base. v1.4.0 added a test that cannot pass on CI, documented six keys that do nothing, and made a published reference authoritative for a schema whose retention keys are still inconsistent with the rest of the format. None of that is careless work; it is what happens when the gates do not run. Phase 0 is not hygiene, it is the precondition for trusting anything else in this document.

## Proposed Solution

### Overview

Twelve phases ordered by severity and dependency: gates and exposure first (a red CI means nothing else can land verified; the Tatari fixtures are a live exposure), then the silent-success criticals in the parse/schedule core, conditional-deps semantics, injection/containment, state integrity, upgrade safety, cfg correctness, Makefile converter truth, TUI/CLI surface, repo hygiene, doc truth, and test-gap closure. Every fix lands with its regression test in the same phase. `otto ci` gates every phase (and after Phase 0, actually can).

### Architecture

No new modules. The structural changes, all inside existing files or extracted from them:

- The scheduler's completion channel payload becomes typed: `Result<String, TaskFailure { name: String, error: eyre::Report, exit_code: Option<i32> }>`, the task name and exit code carried structurally on both arms, never parsed out of strings. Every exit path of the spawned task body sends exactly one message, and handles are reaped via JoinSet so panics are observed.
- `TaskStatus::Skipped` gains provenance (`SkipKind::UpToDate | SkipKind::Unreachable | SkipKind::SerialPredecessor`), and `skipped_set` widens from `HashSet<String>` (`scheduler.rs:613`) to `HashMap<String, SkipKind>` to carry it so foreach aggregation and `when:` classification can distinguish "skipped because cached" (success-like) from "skipped because a prerequisite failed". **Re-anchored 2026-08-29:** the aggregation override at `scheduler.rs:729-730` reads status only, which is precisely why it cannot tell those apart. That override is the fix site, not `classify_edge`.
- **`classify_edge` stops short-circuiting Skipped sources** (`scheduler.rs:176-178`), and instead resolves them against the edge's `when` using the provenance table below. **The code already contains both semantics and they disagree:** the executor's dependency double-check at `scheduler.rs:955-963` already says `(When::Always, Some(TaskStatus::Skipped)) => true` under the comment "when: always is satisfied by any terminal state", while `classify_edge` returns `Unreachable` for the same edge before it ever matches on `when`. Two gates on the same edge, opposite answers. This is a reconciliation, not a new policy.

  **The `Skipped` provenance contract** (this is what `SkipKind` is for; today the code cannot express it, which is why a one-line inversion is not sufficient):

  | Source `SkipKind` | `when: success` | `when: failure` | `when: always` |
  |---|---|---|---|
  | `UpToDate` (file deps satisfied) | Satisfied | Unreachable | Satisfied |
  | `SerialPredecessor` (earlier group member failed/skipped) | Unreachable | Unreachable | Satisfied |
  | `Unreachable` (a prerequisite failed or was skipped) | Unreachable | Unreachable | Satisfied |

  Rationale per column. `UpToDate` is success-like, so it satisfies `success`; this is what the current double-check's `(When::Success, Skipped) => true` at `:957` is groping for without being able to tell the kinds apart. `always` is satisfied by every terminal state, which is the point of `always` and what makes cleanup reliable.

  **The whole `failure` column is Unreachable, deliberately.** An earlier draft of this table marked `SerialPredecessor` and `Unreachable` as satisfying `when: failure`, which would have redefined `when: failure` from "the source task's action failed" to "something upstream prevented this node running". That is a different language and it was never sanctioned. Four independent statements of the opposite invariant, one of them in the code itself:

  - `2026-05-24-conditional-task-dependencies.md:55` (Non-Goals): "`when: failure` fires only on a non-zero exit from the task's action script."
  - Same doc `:86`: "don't run the fixer if the foreach group never actually started."
  - Same doc `:892`: the resolved `--skip` question.
  - **`scheduler.rs:770-773`, in-code:** a skipped virtual parent enters `skipped_set` "so that downstream `when: failure` edges to this parent become Unreachable rather than Pending forever."

  `tests/foreach_aggregation_test.rs:203-204` is titled "A downstream `when: failure` does NOT fire (Skipped is not Failure)" and `:260-261` asserts `fixer == Skipped`.

  **Two further reasons, which are what actually settle it.** First, **no Phase 2 success criterion needs those cells**: the serial-foreach fixer is delivered by the aggregation (`scheduler.rs:727-731` checks `any(Failed)` before `any(Skipped)`, so the fixer's failure edge sees a Failed parent, never a Skipped one), the warm-cache criterion uses the `success` column, the cleanup criterion uses `always`, and the paired-edge criterion is unrelated. The cells were unrequired by the phase that introduced them. Second, they carry real blast radius: if `a` fails, then `b` (holding `when: success` on `a`) becomes `Skipped(Unreachable)`, and every `when: failure` handler attached to `b` would fire. **One failure would fan failure-handlers across the entire downstream cone.**

  Caught in panel round 2. **`when: failure` continues to mean the source task ran and its action exited non-zero.**

  This is also why the serial-foreach bullet still closes: a serial group whose member *failed* aggregates the parent to `Failed`, not `Skipped`, because the aggregation checks `any(Failed)` before `any(Skipped)`. The fixer fires off a Failed parent. It never needed `failure` to accept a skipped source.

  **This table is new design, not a re-anchoring, and is called out as such.** Skip provenance does not exist today: it is `skip_reasons: HashMap<String, String>` (`scheduler.rs:342`, written at `:448`), free text intended for display, with no type distinction any scheduling decision can read. `SkipKind` introduces that distinction. Because six of the nine cells are non-obvious, the contract ships with a **table-driven test asserting all nine cells explicitly** (`classify_edge_skip_provenance_matrix`), not merely the cases the fixes happen to exercise. That test is the artifact that makes this table enforceable rather than aspirational, and it is named in Phase 2's success criteria and Phase 11's inventory.
- Script generation stops templating values: env vars, params, foreach items, and dynamic choice values pass through the process environment (the scheduler already calls `.envs()` at `scheduler.rs:1067`), or where materialization is unavoidable, values are escaped with the same single-quote escaping `otto_serialize_output` already uses.
- `TaskSpecs`/`ParamSpecs` move from HashMap to IndexMap, making serialization deterministic and author-ordered.
- The `FileSystem` port gains atomic write (temp file in the target's own directory + rename); the script cache and all persisted writes route through it.
- A converter diagnostics system: `MakefileParser` tracks line numbers and accumulates warnings; `--strict` (currently a dead flag) promotes warnings to errors.
- **A single `run_root()` helper** replaces the three independent `otto-<hash>` prefix assumptions (`manager.rs:880`, `clean.rs:282`, `pruning.rs:90`) and the three home-dir mechanisms.

### Data Model

- `runs.timestamp` loses its global UNIQUE; run identity keys off `runs.id` (`last_insert_rowid`), which `record_run_complete`/`delete_run` take instead of a wall-clock timestamp. The run's actual directory name (`<project-name>-<hash>`) is recorded at run start so deletion stops reconstructing it wrongly.
- Each migration step and its `set_version` run inside one transaction, and the v1-to-v2 ALTER becomes idempotent (pragma_table_info check before ALTER).
- The DB connection sets `busy_timeout` (named const) and `synchronous=NORMAL` under WAL at open.
- Recorded task rows carry the real exit code (`status.code()` captured where the error is built).

### API Design

- Unknown task names error with near-match suggestions; cycles error at scheduler init (reusing the daggy `add_edge` WouldCycle detection, which **works today and is simply never wired to the execution path**: `otto Graph` on a cyclic file already exits 1 with `WouldCycle`); `tasks: []` with explicit task args runs them.
- Builtin meta-tasks are excluded from `*` default-task expansion, and builtins are routed in main by scanning past global flags.
- `parser::parse` honors its `Result` contract; the remaining `get_matches_from` at `parser.rs:1028` and all 12 `process::exit` calls move to main.
- `nargs` gets wired to clap `num_args` (space-separated per the CLI rule, never `value_delimiter`); `dest` and `constant` are deleted until a consumer exists.
- `history --status` becomes a `ValueEnum` with `ignore_case = true`; choices-bearing params get `ignore_case(true)`.
- `--log-level` flag replaces `RUST_LOG`; the log path derives from an `xdg_data_dir()` helper instead of the banned `dirs::data_local_dir()`.
- **The five inert `otto:` keys** (`jobs`, `home`, `verbosity`, `name`, `about` - `api` was never inert, it gates schema version) are either wired to real behavior or deleted from the schema and from `docs/commands/ottofile-reference.md`. Accepted-and-ignored-but-documented is the worst of the three states. **Resolved in Phase 10:** `jobs` (widely set in committed examples) and `name`/`about` (a real writer already existed in `otto Convert`) were wired; `home` and `verbosity` (zero readers, zero writers, zero committed usage) were deleted.

## Alternatives Considered

### Alternative 1: Fix only criticals, defer hygiene and doc truth
- **Description:** Ship Phases 0-5; batch the rest "as touched."
- **Pros:** Faster to the high-value fixes.
- **Cons:** The hygiene tail IS the disease vector here: a red CI trained the repo to ignore its gates, near-zero logging made every silent failure undiagnosable, and stale docs misdirect future work. "As touched" is how three months of red CI accumulated. **2026-08-29 evidence:** it is now six months, the doc tail grew rather than shrank, and stale `.cursor/rules` files now describe a key that hard-errors.
- **Why not chosen:** No-deferments is the operating rule; every finding gets a phase.

### Alternative 2: Rewrite the Makefile converter on a real parser before fixing it
- **Description:** Replace the line-oriented heuristic parser with a proper make grammar (or shell out to `make -pn`).
- **Pros:** Eliminates the whole corruption class structurally.
- **Cons:** Large new surface for a convenience feature; `make -pn` requires make installed and varies across GNU make versions.
- **Why not chosen:** Phase 7's preprocessing pass + diagnostics makes the converter honest. A grammar rewrite is justified only if converter usage grows; that is the revisit trigger.

### Alternative 3: Move history off SQLite to JSONL
- **Description:** Append-only JSONL per project, no schema, no migrations, no locks.
- **Pros:** Deletes the migration-brick and busy-timeout classes outright.
- **Cons:** stats/history queries become full scans; clean's retention logic reimplements indexing; loses the transactional task/run relationship; the SQLite layer is otherwise sound.
- **Why not chosen:** The defects are fixable at the connection/migration layer; the storage choice was not the problem.

### Alternative 4 (added 2026-08-29): Split this doc into per-phase docs and retire it
- **Description:** Let each phase become its own small doc on the `2026-08-28`/`2026-08-29` model, and delete this one.
- **Pros:** That model demonstrably ships. Both small docs went from draft to tagged release inside two days, while this one has been unbuilt for 2.5 months. Small docs also get real review attention per bullet.
- **Cons:** Loses the cross-phase view that makes the six systemic classes visible; the three `otto-<hash>` sites, the three home-dir mechanisms, and the injection sites across four generators are each one fix precisely because one document sees them all. Twelve separate docs would re-litigate ordering twelve times.
- **Why not chosen, as revised later on 2026-08-29 (author decision, superseding the panel-review revision earlier that day):** this doc is executed directly, phase by phase, as a single implementation run. The panel's earlier revision required each phase to be extracted into its own small doc before implementation; that requirement is removed. The cross-phase view is the reason this doc exists, the per-phase `**Model:**` tags and `Success criteria` already make each phase independently committable, and one commit per phase gives the same legibility an extracted doc would without re-litigating ordering twelve times.
- **Consequence for ship order:** Phase 0 lands first, alone, as its own commit, and the remaining phases follow in order in the same run.

## Technical Considerations

### Dependencies

One addition: `indexmap`, for deterministic author-ordered task/param maps. **It is currently a transitive dependency only** (via `petgraph` -> `daggy` and via `serde_yaml`), so this is a new *direct* dependency, added via `cargo add`. Removals: `tracing`, `tracing-subscriber`, `atty` (RUSTSEC-2021-0145, replaced by `std::io::IsTerminal`), `once_cell` (replaced by `std::sync::LazyLock`), `tokio-test`. `levenshtein` goes from dead to wired.

### Performance

Strictly improvements or neutral: deterministic script hashing makes the content-addressed cache actually hit; `spawn_blocking` for DB writes stops stalling the runtime; the stats N+1 collapses to grouped conditional aggregates; atomic writes add one rename per persisted file. **One measured regression fix promoted from "minor" to scope:** moving env.rs's per-call `Regex::new` to `LazyLock` statics, since deep chains are currently quadratic (12.1s at 100-deep, 22.3s at 150, 45.0s at 200).

### Security

Phases 3 and 5 are the security phases: script-generation injection closed for env values, params, **foreach items, and dynamic choices values**; foreach items rejected or slugified before becoming directory names, closing a path-traversal that currently writes outside the run's `tasks/` tree; command-substitution output no longer re-expanded, closing the parent-env leak; clean's symlink-following deletion fenced to canonicalized paths under the otto root in **both** the fs and DB paths; upgrade gains checksum verification against the per-tarball `.sha256` sibling and an atomic staged rename; the live HTTP client gains timeouts and status checks. Phase 0's removal of employer Makefiles from this confirmed-public repo is exposure cleanup, not a code fix, and lands first. Note the limit of that cleanup honestly: the files entered history on 2025-12-08 and the repo has been public throughout, so deletion stops future exposure and does not undo past exposure. The disclosed content is internal repo names, their Makefile bodies, and a developer's local path layout. No credentials or endpoints were found in them.

### Testing Strategy

Every fix in Phases 0-10 lands with a regression test in the same commit; TDD where the bug is empirically reproducible, which after the 2026-08-29 re-verification is nearly all of them: each `Observed` line above is a failing test waiting to be written. `otto ci` gates every phase by exit code; Phase 0 makes that gate real on CI as well as locally. **Two tests must be changed rather than added**: `tests/serial_foreach_test.rs:216-266` (Phase 2 inverts its assertion) and `test_help_global_flags_no_drift` (Phase 0 makes it runner-portable). Both are called out in their phases so neither looks like an undisclosed deviation during the implementation audit.

See Rollout above. Releases follow the standard flow: phases land as commits on main, `bump` cuts the version after the tranche that closes each behavior-changing group (Phase 0 alone; Phases 1-5 together; the rest as they complete).

- **Release-artifact signature verification** (parked 2026-08-29, raised by the Phase 5 implementer, uncovered by any phase). Phase 5 makes `otto Upgrade` verify a SHA-256 checksum against the per-tarball `.sha256` sibling before installing. **That makes the download tamper-evident, not trusted.** The sibling is served from the same host as the tarball, so anyone who controls the release host controls both, and `verify_binary` then *executes* the downloaded artifact before installing it. The checksum defends against a corrupted transfer, not against a compromised release host or a registry account takeover. Real defense is a detached signature (minisign or cosign) produced at release time and verified against a public key compiled into the binary. `git grep -in 'minisign|cosign|signature|sigstore'` over this document returns nothing: **no phase covers it.**
  **Why parked rather than added to Phase 5:** it is not a code fix in this repo's remediation surface. It requires a signing key and somewhere to keep it, a release-workflow step that signs every asset, a key-rotation story, and a decision about what a verification failure does to users running an unsigned older release. That is its own design doc, and folding it into a phase would repeat exactly the mistake Alternative 4 warns about.
  **Revisit condition:** before otto is recommended for installation outside this repo's authors, or the first time a release is cut from anywhere other than a maintainer's own GitHub Actions run. Recorded here so the checksum work is not mistaken for supply-chain integrity.
- **`--plan`, timeouts, lazy env evaluation, staged parser pipeline.** Never in this doc's scope; they belonged to the missing sibling doc. Recorded here so the scope is not silently absorbed and so the loss is visible.
