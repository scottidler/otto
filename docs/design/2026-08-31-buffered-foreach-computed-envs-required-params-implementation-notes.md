## Phase 1: `params.<title>.required`

### Design decisions
- `required: bool` on `ParamSpec` (`src/cfg/param.rs`), `#[serde(default, skip_serializing_if = "is_false")]`, matching the doc's `ParamView` treatment so a plain param round-trips byte-identically.
- Load-time validation lives in two places, by which of them needs declaration order: `ParamSpec::validate_required` (`src/cfg/param.rs`) checks one param's own shape (FLG, `default:`, zero-capable `nargs`), and `Parser::validate_required_params` (`src/cli/parser/config.rs`) walks each task's params in declaration order for the one cross-param property (required positional after optional positional), calling the former per param on the way. Both run from `load_config_from_path`, beside `validate_foreach_sources`/`validate_no_builtin_params`, so every surface including `--help`/`--tasks` reports the misconfiguration.
- `param_to_arg` (`src/cli/parser/command.rs`) calls `arg.required(true)` unconditionally when `param_spec.required`, relying on load-time validation to have already ruled out the shapes where that would be wrong (FLG, default, zero-capable nargs) — no redundant check at the clap-building site.
- Preflight (`Parser::preflight_required_params`, `src/cli/parser/discovery.rs`) is a new function called at the very top of `process_tasks_with_filter`, before Step 0's `global_envs()`. It answers from `self.pargs` and `self.config_spec.tasks` alone: for each task literally named in `requested_tasks`, if it declares a required param AND its partition in `self.pargs` has length exactly 1 (name only, zero args), it returns `required_param_error` (a new free function in `src/cli/parser.rs`, styled like the existing `unknown_task_error`/`duplicate_task_error`). A partition of length 0 (task not named on the command line at all — dependency-only, or reached via `parse_all_tasks`'s all-task enumeration for `otto graph`) is deliberately NOT the same as length 1 and does not trigger the preflight, matching the design doc's explicit statement that dependency-only and `otto.tasks:` default-selected tasks are unaffected.
- `ParamView` (`src/cli/commands/tasks.rs`) gained `required: bool` with the same `skip_serializing_if = "is_false"` treatment, plus a private `is_false` helper (a second, identical helper was added in `src/cfg/param.rs` — both files needed one and neither imports from the other for this).

### Deviations
- **`docs/commands/ottofile-reference.md` and its drift test updated in this phase, not deferred to Phase 5.** The design doc's own Phase 5 bullet says the reference doc moves 42 -> 45 (all three keys) there. But an existing repo-level test, `ottofile_reference_key_inventory_is_exhaustive` (`src/cfg/task_tests.rs`), destructures `ParamSpec` exhaustively and recovers its on-disk key count from a live `deny_unknown_fields` error; adding `required` as a real field makes that test immediately expect a `ParamSpec` count of 7 and a page total of 43 (not 42), and it fails at `cargo test` if the doc doesn't say so. This is the existing test enforcing its own contract, not a scope choice: the doc row for `params.<title>.required` and the count bump (`ParamSpec` 6->7, total 42->43) are added now, correctly seamed to the one key this phase adds. Phase 5 will move it again from 43 to 45 for the other two keys.
- **Success criterion (f)'s `envs-command` half is exercised with literal `envs:` instead, because `envs-command` does not exist until Phase 2.** The criterion's actual purpose — proving the preflight sits before `global_envs()`, not merely before the clap gate — is fully covered by a literal `otto.envs: {MARK: "$(touch ...)"}"` substitution, which `global_envs()` always evaluates regardless of `envs-command`. `tests/required_param_test.rs::bare_invocation_touches_neither_the_envs_marker_nor_the_choices_command_marker` uses this fixture and its sibling `supplying_the_value_resolves_both_envs_and_choices_command` is the positive control proving the markers aren't just silently broken. Same effect (proves envs resolution didn't fire on the rejected path), correct seam for what's actually buildable in this phase. Worth a targeted `envs-command`-specific repeat once Phase 2 lands, if the Phase 2 implementer wants the exact key named in the criterion text.
- **Criterion (e)'s otto-dev-tree half was verified against a pre-existing local extract, not a fresh checkout at `659c0efd9f0d06012fbc40ae30ccd5c6da2d3fc0`.** The commit is unreachable from `~/repos/tatari-tv/otto-dev`'s remote in this sandbox (`git fetch` reports "Repository not found" — no network egress to that host). A clean extract of the exact tree already existed at `/tmp/claude-1000/odfull` (21 tasks, `.otto.yml` present) from earlier design-doc research; `otto --tasks --format json` against it is byte-identical to `docs/design/tasks-baseline-otto-dev.json` both before and after this phase's changes (`diff` clean), and the task count is 21 with the same 21 names the acceptance criteria section records. This is the same tree the doc's own "Observed on main" evidence was gathered against, just not re-fetched from git. See Open Questions for what remains formally unverified.

### Tradeoffs
- Two small validation functions (`ParamSpec::validate_required` for shape, `Parser::validate_required_params` for cross-param ordering) instead of one — the ordering check needs the task's params in declaration order and the other tasks needing that context already live in `config.rs` (`validate_foreach_sources`, `validate_no_builtin_params`), so splitting kept each function's job to one property instead of threading an "am I the first optional positional so far" accumulator through a function whose other three checks don't need it.
- `required_param_error` takes `&[&str]` and joins with `", "` rather than building a clap-style multi-line usage block — the design doc only requires the error name the missing params; matching clap's exact rendering was explicitly out of scope ("otto's rather than clap's" is the point of criterion (a)).
