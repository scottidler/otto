# Implementation Notes: Buffered Foreach, Computed Envs, Required Params

Running record of decisions, deviations, tradeoffs, and open questions during
execution of `docs/design/2026-08-31-buffered-foreach-computed-envs-required-params.md`.
Append-only.

## Phase 1: `params.<title>.required`

### Design decisions
- `required: bool` on `ParamSpec` (`src/cfg/param.rs`), `#[serde(default, skip_serializing_if = "is_false")]`, matching the doc's `ParamView` treatment so a plain param round-trips byte-identically.
- Load-time validation lives in two places, by which of them needs declaration order: `ParamSpec::validate_required` (`src/cfg/param.rs`) checks one param's own shape (FLG, `default:`, zero-capable `nargs`), and `Parser::validate_required_params` (`src/cli/parser/config.rs`) walks each task's params in declaration order for the one cross-param property (required positional after optional positional), calling the former per param on the way. Both run from `load_config_from_path`, beside `validate_foreach_sources`/`validate_no_builtin_params`, so every surface including `--help`/`--tasks` reports the misconfiguration.
- `param_to_arg` (`src/cli/parser/command.rs`) calls `arg.required(true)` unconditionally when `param_spec.required`, relying on load-time validation to have already ruled out the shapes where that would be wrong (FLG, default, zero-capable nargs) — no redundant check at the clap-building site.
- Preflight (`Parser::preflight_required_params`, `src/cli/parser/discovery.rs`) is a new function called at the very top of `process_tasks_with_filter`, before Step 0's `global_envs()`. It answers from `self.pargs` and `self.config_spec.tasks` alone: for each task literally named in `requested_tasks`, if it declares a required param AND its partition in `self.pargs` has length exactly 1 (name only, zero args), it returns `required_param_error` (a new free function in `src/cli/parser.rs`, styled like the existing `unknown_task_error`/`duplicate_task_error`). A partition of length 0 (task not named on the command line at all — dependency-only, or reached via `parse_all_tasks`'s all-task enumeration for `otto graph`) is deliberately NOT the same as length 1 and does not trigger the preflight, matching the design doc's explicit statement that dependency-only and `otto.tasks:` default-selected tasks are unaffected.
- `ParamView` (`src/cli/commands/tasks.rs`) gained `required: bool` with the same `skip_serializing_if = "is_false"` treatment, plus a private `is_false` helper (a second, identical helper was added in `src/cfg/param.rs` — both files needed one and neither imports from the other for this).

### Deviations
- **`docs/commands/ottofile-reference.md` and its drift test updated in this phase, not deferred to Phase 5.** The design doc's own Phase 5 bullet says the reference doc moves 42 -> 45 (all three keys) there. But an existing repo-level test, `ottofile_reference_key_inventory_is_exhaustive` (`src/cfg/task_tests.rs`), destructures `ParamSpec` exhaustively and recovers its on-disk key count from a live `deny_unknown_fields` error; adding `required` as a real field makes that test immediately expect a `ParamSpec` count of 7 and a page total of 43 (not 42), and it fails at `cargo test` if the doc doesn't say so. This is the existing test enforcing its own contract, not a scope choice: the doc row for `params.<title>.required` and the count bump (`ParamSpec` 6->7, total 42->43) are added now, correctly seamed to the one key this phase adds. Phase 5 will move it again from 43 to 45 for the other two keys.
- **Success criterion (f)'s `envs-command` half is exercised with literal `envs:` instead, because `envs-command` does not exist until Phase 2.** The criterion's actual purpose — proving the preflight sits before `global_envs()`, not merely before the clap gate — is fully covered by a literal `otto.envs: {MARK: "$(touch ...)"}"` substitution, which `global_envs()` always evaluates regardless of `envs-command`. `tests/required_param_test.rs::bare_invocation_touches_neither_the_envs_marker_nor_the_choices_command_marker` uses this fixture and its sibling `supplying_the_value_resolves_both_envs_and_choices_command` is the positive control proving the markers aren't just silently broken. Same effect (proves envs resolution didn't fire on the rejected path), correct seam for what's actually buildable in this phase. Worth a targeted `envs-command`-specific repeat once Phase 2 lands, if the Phase 2 implementer wants the exact key named in the criterion text.
- **Criterion (e)'s otto-dev-tree half was verified against a pre-existing local extract, not a fresh checkout at `659c0efd9f0d06012fbc40ae30ccd5c6da2d3fc0`.** The commit is unreachable from `~/repos/tatari-tv/otto-dev`'s remote in this sandbox (`git fetch` reports "Repository not found" — no network egress to that host). A clean extract of the exact tree already existed at `/tmp/claude-1000/odfull` (21 tasks, `.otto.yml` present) from earlier design-doc research; `otto --tasks --format json` against it is byte-identical to `docs/design/tasks-baseline-otto-dev.json` both before and after this phase's changes (`diff` clean), and the task count is 21 with the same 21 names the acceptance criteria section records. This is the same tree the doc's own "Observed on main" evidence was gathered against, just not re-fetched from git. See Open Questions for what remains formally unverified.

### Tradeoffs
- Two small validation functions (`ParamSpec::validate_required` for shape, `Parser::validate_required_params` for cross-param ordering) instead of one — the ordering check needs the task's params in declaration order and the other tasks needing that context already live in `config.rs` (`validate_foreach_sources`, `validate_no_builtin_params`), so splitting kept each function's job to one property instead of threading an "am I the first optional positional so far" accumulator through a function whose other three checks don't need it.
- `required_param_error` takes `&[&str]` and joins with `", "` rather than building a clap-style multi-line usage block — the design doc only requires the error name the missing params; matching clap's exact rendering was explicitly out of scope ("otto's rather than clap's" is the point of criterion (a)).

## Phase 2: `otto.envs-command`

### Design decisions
- **Two commits, as the doc's Rollout Plan requires.** `74affac` is the `base_dir()` cwd fix alone (`src/cli/parser.rs`'s `global_envs`, plus the three `tests/envs_command_test.rs` cases that pin it), so the disclosed behavior change is reviewable and revertable on its own. The second commit is `envs-command` itself.
- `run_command_stdout` (`src/cfg/resolver.rs`) now owns the shared execution contract (guard chain, `sh -c`, `.current_dir(cwd)`, `.envs(envs)`, loud non-zero exit with trimmed stderr detail, stderr passthrough on success) and returns raw stdout; `run_lines_command` is a five-line wrapper that adds the `.lines().map(str::trim).filter(...)` foreach and choices want. `tests/foreach_command_test.rs` and `tests/dynamic_choices_test.rs` pass untouched across the split (`git diff --name-only HEAD` on both files is empty).
- `ENVS_GUARD_VAR = "OTTO_ENVS_COMMAND"` sits beside `FOREACH_GUARD_VAR` and `CHOICES_GUARD_VAR` in `src/cfg/resolver.rs`. The guard *key* is a fixed literal, `ENVS_GUARD_KEY = "otto.envs-command"` in `src/cli/parser.rs`, because there is exactly one resolution per invocation rather than one per task.
- `evaluate_envs` (`src/cfg/env.rs`) gained a third parameter, `base_overrides: &HashMap<String, String>`, exactly as the doc specifies. It is layered onto `inherited` (the `env::vars()` map) before evaluation, and it is also the *floor* of the returned map: `let mut result = base_overrides.clone(); result.extend(evaluated)`. That second half is what makes a computed key with no literal counterpart actually reach a task body, since `evaluate_envs` previously returned only the declared keys. All 21 existing call sites pass `&HashMap::new()` and are byte-identical in behavior.
- `parse_env_assignments` (`src/cfg/env.rs`) is a free function next to `evaluate_envs`, not a method on the parser: it is a pure `&str -> HashMap` with no I/O, so it gets its own 14 unit tests rather than only being reachable through a subprocess.
- Resolution happens in `Parser::resolve_envs_command` (`src/cli/parser.rs`), called from inside the `self.resolver.global_envs(|| ...)` initializer ahead of `evaluate_envs`, per the doc. It does NOT touch `DynamicResolver`'s `RefCell` caches; the `OnceCell` already gives once-per-invocation, pinned by `the_envs_command_runs_at_most_once_per_invocation` (a fixture where a `foreach.command` and a task body both force the map, and the command appends to a counter file).
- The `global_envs` fast path now short-circuits only when *both* `otto.envs` and the computed map are empty, so an ottofile with `envs-command` and no `envs:` block still gets its variables (`computed_envs_work_without_any_literal_envs_block`).
- Three `run_command_stdout` unit tests in `src/cfg/resolver_tests.rs` are `#[serial]`: the recursion test mutates the process-global `OTTO_ENVS_COMMAND`, and without the shared lock it raced its two siblings, which use the same guard var (observed failing, then fixed — not theoretical).

### Tradeoffs
- **Layering applied at both ends of `evaluate_envs` (seed `inherited`, and floor the result) rather than merging the computed map into the returned value at the `global_envs` call site.** Merging outside would have kept `evaluate_envs`'s signature, but then a shadowing literal that self-references (`FOO: '$(echo "${FOO:-fallback}")'`) could not see the computed value, since `evaluation_context` seeds from `inherited`, which the call site cannot reach. That is exactly criterion (f), and it is why the doc calls for the signature change.
- **21 mechanical call-site edits (18 of them in `src/cfg/env_tests.rs`) instead of keeping a two-argument `evaluate_envs` wrapper beside a three-argument variant.** Two spellings of one function is the kind of near-duplicate name that stops telling the truth about which one to call; the doc names the signature change explicitly, so the churn is taken once.
- **A key with trailing whitespace (`FOO =bar`) is a loud error, not a trimmed key.** Values are literal, so trimming one side of the `=` and not the other would be an inconsistency the user cannot see. Leading whitespace *before* the key is still skipped, since the doc says so and indented generator output is common.

## Phase 3: Display-order map and the `buffer` key

### Design decisions
- **The display-order map is threaded as a per-task field, mirroring `serial_group`/`serial_index`, not as a bare `HashMap` handed to a new scheduler constructor parameter.** `expand_foreach_tasks_with_serial` (`src/cli/parser/foreach.rs`) already returns `SerialMembership` alongside its `TaskSpecs`; it now also returns a third value, `DisplayOrderMap = HashMap<String, Vec<String>>` (`src/cli/parser.rs`), built at the same site `subtasks` already exists (right before it is consumed by `.into_iter()`), so the recorded order can never drift from the order `expand_foreach_with_items` (`src/cfg/task.rs`) assigned each subtask's `OTTO_FOREACH_INDEX` in. `process_tasks_with_filter` (`src/cli/parser/discovery.rs`) sets a new field, `Task.foreach_display_order: Option<Vec<String>>`, on the virtual parent task from that map, exactly where `serial_group`/`serial_index` are set from `SerialMembership` a few lines above.
- **Every foreach expansion gets a display-order entry, not only `buffer: true` ones.** The design doc's Phase 3 bullet says the map comes "from the enumeration that already produces `OTTO_FOREACH_INDEX`", which runs for parallel and serial foreach alike (per the doc's own Verified facts). Gating population on `buffer` would have made the map's presence a second, redundant signal for something `ForeachSpec.buffer` already says; population is unconditional, so `foreach_display_order` answers "was this a foreach parent" and `buffer` alone answers "should Phase 4 replay it".
- **`foreach_display_order` is carried into `executor::task::Task` (`src/executor/task.rs`) through the existing `From<cli::parser::Task> for executor::task::Task` conversion**, the single documented site every runtime path (plain execution, TUI, graph) goes through, so the scheduler side (which is what actually constructs `TaskScheduler`) receives it the same way `tty`/`serial_group`/`serial_index` already do. Nothing in `src/executor/scheduler.rs` reads the new field yet; it is inert cargo, exactly as the phase's success criteria require.
- **`buffer: bool` on `ForeachSpec`** (`src/cfg/task.rs`), `#[serde(default)]`, `Default` impl updated. Validation (`Parser::validate_foreach_buffer`, `src/cli/parser/config.rs`) walks `config.tasks` and rejects `foreach.buffer: true` + `tty: true` on the same task, naming both keys in the error text, called from `load_config_from_path` beside `validate_required_params` so `--help` reports it too (shape-only, executes nothing, matching the existing `validate_foreach_sources`/`validate_required_params` pattern).

### Deviations
- **`docs/commands/ottofile-reference.md` and its drift test updated in this phase, not deferred to Phase 5**, for the same forced reason Phase 1 and Phase 2 each recorded: `ottofile_reference_key_inventory_is_exhaustive` (`src/cfg/task_tests.rs`) destructures `ForeachSpec` exhaustively and recovers its on-disk key count from a live `deny_unknown_fields` error, so adding `buffer` fails the build until the page says `ForeachSpec` 8 and total 45. Phase 2 took the total to 44; this phase takes it to 45, completing the count the design doc's own API Design section states as the final number — nothing is left for Phase 5 to bump on this axis.
- **The display-order map is a field on `Task`, not a new parameter threaded into `TaskScheduler::new` or `execute_all`.** The design doc's own words ("threaded to the scheduler") are satisfied by the same seam `serial_group`/`serial_index` already use: those two fields are *also* "a map" conceptually (`SerialGroups::new(&self.tasks)` reconstructs a `HashMap<String, Vec<String>>` from per-task fields at the top of `execute_all`, `src/executor/scheduler.rs`). Phase 4's replay cursor can reconstruct its own `HashMap<String, Vec<String>>` from `self.tasks` the same way, with no scheduler constructor signature change. Same effect, correct seam.

### Tradeoffs
- **`foreach_display_order` was added to both `cli::parser::Task` and `executor::task::Task`, plus their `Task::new` constructors and the `From` conversion, instead of only the executor-side struct.** `serial_group`/`serial_index`/`tty` all round-trip through both structs already; adding the field to only one side would have made this one map arrive at the scheduler through a different, undocumented path than every sibling field, which is exactly the kind of drift the `From` impl's own doc comment ("single source of truth ... so a field added to one struct can't be silently dropped") warns against.
- **Validation is a whole-config pass over `config.tasks`, not a method on `ForeachSpec` itself** (unlike `ForeachSpec::validate_sources`). `buffer`'s conflict is with `tty`, which lives on `TaskSpec`, not `ForeachSpec`; a `ForeachSpec`-scoped method has no access to it, so the check has to live at the same level `validate_required_params`'s cross-field check already does.

## Phase 4: Buffered capture and ordered replay

### Design decisions
- **`foreach.buffer: true` reaches the scheduler as a new `Task.buffered: bool`, on the virtual parent AND on every subtask.** The key itself does not survive expansion: `expand_foreach_with_items` (`src/cfg/task.rs`) clones the spec with `foreach = None`, and `as_virtual_parent()` drops `foreach` too, so by the time the scheduler sees a task nothing on it says "buffered". `expand_foreach_tasks_with_serial` (`src/cli/parser/foreach.rs`) now records the buffered parent names while the spec is still in hand, and `process_tasks_with_filter` (`src/cli/parser/discovery.rs`) stamps the flag onto the parent and its subtasks (keyed by `parent_task_name`, since a subtask is `<parent>:<item>`). `foreach_display_order` alone could not carry this: Phase 3 populates it for every foreach, buffered or not.
- **`expand_foreach_tasks_with_serial` returns a named `ForeachExpansion` struct instead of growing to a four-tuple** (`src/cli/parser.rs`). Phase 3 had already taken it to three positional values.
- **One process-wide `TERMINAL_LOCK` in `src/executor/output.rs`, taken by all seven terminal-writing sites.** `terminal_lock()` recovers from poisoning rather than propagating it: the lock guards write ordering only, so a panic while held breaks no invariant, and refusing to print for the rest of the run would be the worse failure.
- **The five scheduler-side writing sites funnel through one helper, `report_status_line` (`src/executor/scheduler/replay.rs`).** For a buffered subtask it stashes the already-formatted status line so the line travels with the block; for everything else it prints immediately under the lock. That is also what makes "driven from all four terminal-transition sites" one call rather than four transcriptions: the success arm, the failure arm, `mark_skipped`, and the up-to-date skip all call it.
- **`ReplayCursor` is a plain local on the `execute_all` frame** beside `completed_set`/`failed_set`/`skipped_set`, built by `ReplayCursor::new(&self.tasks, self.tui_mode)` the same way `SerialGroups::new(&self.tasks)` reconstructs its map from per-task fields. No `Arc<Mutex>`, no scheduler constructor change. Empty (and therefore inert) under `--tui`, and each group's item list is filtered to the tasks actually in the run, because an item that will never reach a terminal state would stall its group's cursor forever.
- **Replay streams with `std::fs` + a bounded reader, never `TaskStreams::read_output`.** `read_bounded_chunk` reads to the next newline or `REPLAY_CHUNK_BYTES`, whichever comes first, using `fill_buf`/`consume`; `BufRead::read_until` would be simpler and unbounded. A log line longer than the cap is emitted in pieces, prefixed once at its start. `read_output` is untouched, for its one existing caller.
- **A block's stdout replays to stdout and its stderr to stderr**, preserving the stream each byte was captured from, and its status line goes to whichever stream it goes to unbuffered (failures to stderr, everything else to stdout). `write_replay_blocks` holds both handle locks for the whole batch, inside one `spawn_blocking` closure, under the process-wide lock.
- **Truncation markers, the killed-child paths line, and the did-not-start line all go to stderr**, alongside otto's other diagnostics (the failure message, the run-cancelled message), rather than into the task's stdout stream.
- **`abandon_run` drains the report channel with `try_recv` before aborting the bodies.** That is what turns the design doc's "report sent but not yet consumed" state into a complete block instead of a did-not-start line; nothing else can tell it apart, since a successful body does not write its own status into the status map.
- **The `select!` cancel arm reports rather than returning**, via a small `Wakeup` enum, because `abandon_run` needs `&mut rx` and `rx` is borrowed by the `recv()` future for the whole `select!`. `Option<TaskReport>` could not carry it: `None` already means "channel closed", which is fatal rather than cancelled.
- **The cancellation flush's decision is a pure function, `plan_cancelled_group`.** It maps the doc's six states onto four outcomes from three signals (already emitted, a recorded transition, and `Running` + "the child ever opened a log"), in item order, one entry per item, never stopping early. Separating it from the writing is what makes the property unit-testable without capturing process file descriptors.

### Deviations
- **A `Task.buffered` flag was added; the design doc did not name one.** It names `suppress_terminal: true` for buffered subtasks and the display-order map for the parent, but the flag is the only thing that can carry `buffer: true` past an expansion that deletes `foreach`. Same effect, correct seam.
- **The truncation marker, the killed-child line, and the did-not-start line go to stderr, not into the block's stdout run.** The doc says the marker "ends the block" without naming a stream; stderr matches every other otto-authored diagnostic. In a merged terminal view (which is what the contiguity property is about, and how criterion (d) is asserted) it still lands at the end of the block.
- **Criterion (d) is asserted against a MERGED capture (both descriptors pointing at one file), not against `Output`'s two separate pipes.** A block split by a line on the other stream is split for the reader, and two separate pipes cannot show that. The test also had to be strengthened twice before it bit at all: the original fixture's writers never overlapped a replay.
- **The doc's break-the-code check "removing the lock from `scheduler.rs:1112` alone must FAIL criterion (d)" does not bite against this implementation, for two structural reasons, and a stronger equivalent was run instead.** (1) The five scheduler-side status lines are already serialized against replay by the ready loop itself: the success/failure/skip handlers `await` the replay join handle inline, so no scheduler line can print while a replay is in flight. (2) `write_replay_blocks` holds Rust's own stdout and stderr handle locks for the whole block, so a live `print!`/`eprint!` writer is already blocked for its duration. All seven sites take the process-wide lock as the doc specifies; it is a second, explicit guard rather than the only one. The check that does bite is recorded under Success criteria below.
- **Criterion (f) is driven through `cancel_signal()`, not through a real SIGINT.** See Open questions: otto installs no SIGINT handler outside `--tui`, so a SIGINT at a plain `otto` cannot reach `abandon_run` at all today. `cancel_signal()` is the one trigger the scheduler has, and it is what the existing cancellation tests use.
- **Criterion (f)'s test redirects the process's real file descriptors** (`tests/foreach_buffer_cancel_test.rs`), because replay writes through a locked `io::stdout()` which the test harness's `print!` capture does not intercept. That is process-global, so it is the only test in its file.
- **Criterion (e)'s per-item gate is the up-to-date skip**, not a dependency edge: every subtask of a foreach inherits the same `before:` list, so an edge gates the whole group rather than its first item. The whole-group `mark_skipped` path is covered by its own test alongside it, so both no-report skip paths are exercised.
- **Criterion (b)'s barrier is a shared rendezvous directory rather than a FIFO.** Same property, same failure mode (the run completes only if all three items are live at once, and each item fails on its own timeout otherwise), without FIFO open-blocking semantics inside a task body. Verified to bite: flipping the fixture to `parallel: false` fails it with `alpha never met the others`.

### Tradeoffs
- **The status line is stashed as a preformatted `String` rather than as a status enum re-rendered at replay time.** Preformatting keeps `status_label`/`--no-prefix`/`task_outcome_word` in exactly one place per site and keeps the skip paths' free-text detail (`skipped (dep gate failed; ...)`) intact; the cost is that `PendingBlock` carries display bytes rather than a status value.
- **Cancellation tells a killed child from an unstarted body by whether `stdout.log` exists**, rather than by tracking child state in `ActiveTasks`. `ActiveTasks` tracks spawned bodies only, and widening it to track children would touch the scheduler's execution structures, which this doc's Phase 3 decision explicitly rules out. `process_output` creates the log the moment the child is spawned, so the file is a faithful proxy.
- **`plan_cancelled_group` takes `&dyn Fn(&str) -> bool` for the log-existence probe** so the test does not have to lay out a run directory. One dynamic call per cancelled item, on a path that runs once per cancelled run.
- **`OutputType` gained `Copy`/`Eq`.** It is a two-variant fieldless enum; `DrainIssue` wants to be `Copy`, and the one `.clone()` call site was updated.

### Open questions
- **otto has no SIGINT handler outside `--tui`.** `tokio::signal::ctrl_c` is spawned only in the TUI path (`src/app.rs:579-588`), and the only production caller of `cancel()` is the dashboard closing (`src/app.rs:609`). A SIGINT at a plain `otto` therefore terminates the process outright and never reaches `abandon_run`, so the cancellation flush this phase built is currently reachable only from the TUI path (where buffering is inert) and from `cancel_signal()`. Wiring SIGINT to `cancel_signal()` on the non-TUI path would change teardown behavior for every run, not just buffered ones, and is not in this doc's scope. Flagging it for a decision.
- **The five scheduler-side terminal writes are serialized against replay by the ready loop, not by the lock** (see Deviations). If a future change moves replay off the inline `await` (say, fire-and-forget), the lock becomes load-bearing there; it is in place for exactly that reason, but no current test can prove it.
