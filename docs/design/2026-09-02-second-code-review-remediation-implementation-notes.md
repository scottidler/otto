## Phase 1: Executor process boundary: stdin and SIGTERM

### Design decisions
- Both stdin routes live in ONE `if !tty` block — `src/executor/scheduler/task_execution.rs`, `execute_task` — because the doc's round-3 S2 finding is that they are not two parallel halves: `setsid`'s guarantee only holds for a bash body if fd 0 is not a terminal, since a session leader acquires a controlling terminal by opening one at startup. Keeping them adjacent under one comment is what stops a later edit from deleting one and leaving the other looking sufficient.
- `setsid` goes through `tokio::process::Command::pre_exec` rather than `std::os::unix::process::CommandExt` — `task_execution.rs`, `execute_task` — tokio's `Command` exposes `pre_exec` as an inherent unsafe method, so no extension trait import is needed and the `#[cfg(unix)]` sits on the one `unsafe` block.
- One helper, two call sites — `src/app.rs`, `next_stop_signal` and `install_stop_handler` — the plain path and the `--tui` path had two hand-written signal tasks that already disagreed (one cancelled, one only set a flag). They now differ only in two closures: what to do after the first cancel (`--tui` sets its quit flag) and what to undo before the second-signal exit (`--tui` hands the terminal back). The doc's success criterion is a count of at least 1, precisely so this factoring is allowed.
- Signal numbers come from `libc::SIGINT` / `SIGTERM` / `SIGHUP` rather than literals — `app.rs`, `next_stop_signal` — the number is only ever used to build the 128 + n exit and `libc` is already a direct dependency.
- The three plain/TUI signal tests read liveness from `/proc/<pid>/cmdline` content, not pid existence — `tests/sigint_cancel_test.rs`, `still_running` — same rule `cancel_reaping_test.rs` states: pids recycle and a zombie still has a `/proc` entry. That makes those three tests `#[cfg(target_os = "linux")]`, matching the existing reaping suite.
- The grandchild mark in the new signal fixture is `sleep 603` — `tests/sigint_cancel_test.rs`, `GRANDCHILD_MARK` — distinct from `cancel_reaping_test.rs`'s 601 and 602 so the two binaries cannot read each other's processes when cargo runs them concurrently.
- The pty read tests set `HOME` to the fixture directory as well as `OTTO_HOME` — `tests/tty_task_test.rs`, `PtyRun::start` — the `bash -ic` case sources the developer's own startup files, which on this machine printed seven lines of zsh-only syntax errors. Pointing `HOME` at the fixture makes the case read the same nothing everywhere.
- `tests/cancel_reaping_test.rs` was left byte-for-byte untouched, including its module comment's historical reference to `cmd.process_group(0)`, which reads as narrative about v2.1.0 and is still true as history. `git diff --name-only tests/cancel_reaping_test.rs` is empty.

### Deviations
- **Renamed `restore_terminal_on_panic` to `restore_terminal_best_effort`** (`src/tui/mod.rs`, plus its two hook call sites and one test). The doc says the second-signal escape hatch "restores the terminal first (`terminal.restore()`)", but the signal task is a detached `tokio::spawn` that cannot own the `TerminalGuard`; the correct seam is the existing free function that goes through the same `claim_terminal_restore` mechanism. Its old name would then have been a lie about who calls it. Same effect, correct seam.
- **Renamed `install_interrupt_handler` to `install_stop_handler`** (`src/app.rs`, and the one prose reference at `src/executor/scheduler.rs`'s `CANCEL_GRACE`). It handles three signals now; "interrupt" named one of them.
- **Timeouts in the new pty read tests are 30s, not the doc's "within one second".** The behavior being excluded is an *unbounded* hang (before this phase the same fixtures ran until an external `timeout` killed them), so the bound only has to be finite; one second would flake on a loaded machine on otto's startup alone. Measured locally the whole `tty_task_test` binary, all eleven tests, finishes in 1.80s.
- **Four present-tense comments outside the doc's list were corrected** because `process_group(0)` is no longer what happens: `scheduler.rs` (`ChildHandle::pid`'s doc and `signal_child`'s SAFETY note), `scheduler/support.rs` (`abandon_run`'s doc), and `app.rs` (the stop handler's doc). The doc names only `task_execution.rs:274`; leaving the other four would have left the dead mechanism written down in four places.
- **Test placement follows the doc, including the file name.** The SIGTERM, SIGHUP and `--tui` SIGHUP tests are in `tests/sigint_cancel_test.rs`, whose name now covers only one of the four signals it tests. Renaming the file was not in scope for this phase; the module comment was rewritten to say what the file actually covers.

### Tradeoffs
- **`next_stop_signal` re-registers its `Signal` streams on the second call, rather than a struct holding them across both awaits.** A signal arriving in the microsecond gap between the two calls is absorbed by tokio's process-level handler (which is installed once and never uninstalled) rather than killing otto, so the gap cannot resurrect the default disposition; a struct would have added a type for no behavior change. The pre-existing `ctrl_c()`-twice code had exactly this shape.
- **`bash -ic` is asserted on the substring `/dev/tty`, not on the whole stream** (`a_non_tty_task_opening_dev_tty_from_an_interactive_shell_fails_too`), because an interactive bash with no controlling terminal also prints its own job-control warning. The doc's round-3 N1 nit says the same.
- **Change (b) of the TUI fix — cancel-then-propagate at the draw-error path — has no isolating regression test, and I could not build one.** Measured: with (b) reverted but (a) in place, killing the pty master under `--tui` still reaped the grandchild in 3 runs of 3, because the signal task's `cancel()` wins the race against process exit. (b) converts that race into a guarantee by awaiting the scheduler handle before propagating; it is determinism, not mechanism, so nothing observable goes red when only it is removed. Recorded rather than papered over.

### 2026-09-04 amendment: a real hangup

## Phase 2: Executor data passing and buffered replay

### Design decisions
- **`is_identifier` lives in `naming.rs` as `pub(crate)`, exactly as the doc specifies** — `src/naming.rs:is_identifier` — Phase 4 reuses it for `foreach.as`, so the signature is fixed now. The two copies it replaces are gone: `cfg/env.rs`'s `is_valid_env_key` was deleted and its one call site rewritten, `executor/action.rs`'s `validate_identifier` kept its error message (which is the caller's context: kind, task name, name) and now asks `naming::is_identifier` for the verdict.
- **The per-byte fold is a separate function with its own name, `fold_to_var_name`** — `src/executor/scheduler.rs:fold_to_var_name` — panel round 1 finding S1. Its doc comment says in so many words why it is not `is_identifier`: the whole-name rule rejects a leading digit, and applying it byte by byte would fold `OTTO_INPUT_UP_2024` to `OTTO_INPUT_UP____`. `naming_tests.rs:is_identifier_is_a_whole_name_rule_not_a_per_byte_class` asserts the distinction rather than leaving it to the comment.
- **The fold is per BYTE, not per `char`** — `src/executor/scheduler.rs:fold_to_var_name` — the reader is `LC_ALL=C tr` in `builtins.sh`, which folds bytes. `é` is two bytes, so `tr` emits two underscores; a `chars()` fold would emit one, the prefixes would differ, and the reader would match nothing at exit 0 — the same silent-empty failure the `-`-only fold had. Uppercasing is `to_ascii_uppercase` for the same reason (`ß` uppercases to `SS` in Rust and to itself under `LC_ALL=C tr`).
- **The bash side complements the class instead of enumerating it** — `src/executor/action.rs`, `otto_deserialize_input` — `LC_ALL=C tr -c '[:alnum:]_' '_'` replaces the two `${task_upper//x/_}` expansions. Enumerating was the bug: `:` was simply not on the list. `tr -c` is POSIX and bash-3.2-safe, so the macOS constraint the surrounding comment guards is unaffected.
- **`suppress_terminal` is computed in `try_start_ready_task`** — `src/executor/scheduler/support.rs` — see Deviations; it is the frame that already holds `&mut ReplayCursor` and is the sole caller of `execute_task` (both arms).
- **The parity test now pins itself to the shell that ships** — `src/executor/action_tests.rs:builtins_input_fold_matches_the_writer_fold` — it holds the fold pipeline as a `SHELL_FOLD` const, asserts the generated `builtins.sh` still contains that exact text, and only then runs it against `fold_to_var_name`. Before, the test held a private copy of the shell fold with nothing tying it to the real one, so reverting `builtins.sh` alone could have left the test green.

### Deviations
- **The doc says compute `suppress_terminal` "in `execute_all` where the cursor is built"; it is computed in `try_start_ready_task`.** Same effect, correct seam: `execute_all` builds the cursor (`scheduler.rs:1445`) and hands it down, but it never calls `execute_task` — `try_start_ready_task` is the only caller, in both its `Ok(true)` and its `Err(_)` arm, and it already takes `cursor: &mut ReplayCursor`. Computing it in `execute_all` would mean computing it for a task that has not been selected to start yet.
- **The doc's Rust spelling is `c.is_ascii_alphanumeric() || c == '_'` over chars; the implementation is the same predicate over bytes.** Reason under Design decisions: a char-wise fold does not agree with `LC_ALL=C tr` for multibyte input, and byte-exact agreement with the reader is the whole requirement.
- **The doc lists the parity fix as two call sites; a third file changed.** `src/executor/action_tests.rs` held a hand-copied duplicate of both folds and pinned the old rule, so it would have gone red on the correct behavior. Inverted by name rather than deleted: it still tests fold parity, now against the real code on both sides, with `up:alpha` and `up_2024` added as cases.
- **Two tests were added to `tests/foreach_buffer_test.rs`, not one.** The doc asks for "requesting one item of a buffered foreach prints its output". `test_asking_for_the_parent_still_buffers_the_whole_group` is its complement: without it, deleting suppression outright would also pass.

### Tradeoffs
- **`fold_to_var_name` lives in `scheduler.rs` beside its only caller, not in `naming.rs` beside `is_identifier`** vs putting both name rules in one module — the doc is explicit that the two must not be merged, and `naming.rs` is about *subtask* names, while this is the writer's half of a wire format shared with `builtins.sh`. Keeping it next to `json_to_env` keeps the two halves of that format one screen apart. It is `pub(crate)` only so the parity test can call the real function instead of a copy.
- **The parity test asserts `builtins.sh` contains `SHELL_FOLD` verbatim, indentation and all** vs extracting the pipeline by parsing the file — a literal-text assertion is brittle to reindentation, but it fails loudly with a message that says exactly what to do, whereas a parser would silently test a fragment it no longer found. The `#[tokio::test] #[serial]` cost of generating a real `builtins.sh` is the price of not testing a copy.
- **`tests/subtask_output_test.rs` is a new file rather than a case in `tests/foreach_aggregation_test.rs`** (the doc allows either) — the bug is a foreach subtask *feeding a consumer*, which is the input/output surface, not the aggregation surface. It carries a second test on the generated `.env` file itself, so the fold is pinned at the file as well as at the consumer.

## Phase 3: cfg env evaluator

### Design decisions
- **The deferral check runs on the raw value, before `evaluate_single_env_value`** — `src/cfg/env.rs:evaluate_envs` — `referenced_vars(raw_value)` scans `$(...)` bodies under the same rules as the expander, so a declared sibling named inside a command body is visible before anything executes. The old order executed first and let the empty read stand as the answer, which is why the result depended on which key the sorted pass reached first.
- **Only a DECLARED name defers; the key's own name never does** — same loop — the predicate is `name != var_name && envs.contains_key(name) && !evaluated.contains_key(name)`. An inherited name resolves inside the command from the inherited environment (the `$(echo "${SOME_PROFILE:-default}")` idiom), so it must not wait; a self-reference reads the inherited seed `evaluation_context` plants, which is the only value it will ever get, so deferring on it would spin to the no-progress branch and be misreported as a cycle.
  - **2026-09-04 amendment: the same exclusion was missing from the cycle reporter.** The deferral rule excludes a key's own name, and `find_reference_cycle` did not, so it followed a legal self-reference and reported it as the cycle while the real one went unnamed. Measured with `envs: {AAA: '$AAA $BBB', BBB: '$CCC', CCC: '$BBB'}` and `AAA` seeded from the environment: v2.2.1 and `a7df373` both fail with `Circular dependency between environment variables: AAA -> AAA`; fixed says `BBB -> CCC -> BBB`. Error text only, never a wrong value, and latent rather than a regression. The walker now skips an edge from a key to itself, matching the deferral predicate. `env_tests.rs:a_legal_self_reference_is_not_reported_as_the_cycle` pins it.
- **An evaluation error is terminal, not "wait"** — same loop, the `Err` arm — once the check above has passed, every declared reference the value makes is resolved, so the only remaining errors are a command that exited non-zero and a reference to a name that is neither declared nor inherited. Both return immediately, with the message the partial-resolution fallback already used (`Failed to resolve environment variable '<key>': <cause>`), so no pinned string changed.
  - **2026-09-04 amendment: reverted to "park, then retry once".** The bullet above was wrong about what remains: a command can read a declared sibling WITHOUT spelling its name (`$(env | grep '^Z_HOST=' ...)`, or a tool reading `VAULT_ADDR` from its environment), and the reference scan cannot see that. Measured old vs new: `A_ENDPOINT: "$(env | grep '^Z_HOST=' | cut -d= -f2 | grep .)"`, `Z_HOST: vault.example` printed `A_ENDPOINT=[vault.example]` on v2.2.1 and failed the load on the first cut of 2.3.0 (`Command ... failed with exit code 1`). The `Err` arm now parks the key; when nothing else is pending the parked keys run once more against the complete environment, and only a failure then is returned. A key deferred on a parked key reports the parked failure, not a cycle. Bound: two runs of a failing command, not one per pass (the pre-2.3.0 shape) and not one (the first cut). `a_failing_command_runs_exactly_once` became `a_failing_command_runs_once_more_after_its_siblings_resolve` (asserts 2) plus `a_failing_command_with_no_siblings_runs_exactly_once` (asserts 1); `a_command_reading_a_sibling_from_its_environment_waits_for_it` pins the regression. The success criterion below that reads "exactly one marker file" is superseded: it is one for a lone key and two beside siblings.
  - **2026-09-04 amendment: the reference scan reports the variable a parameter expansion reads.** `referenced_vars` went through the expander's `${...}` arm, which takes everything up to `}` as the name, so `${ZZZ:-fallback}` scanned as `ZZZ:-fallback`, no declared key matched, and the command ran before `ZZZ` resolved: measured `AAA: '$(echo "got:${ZZZ:-fallback}")'`, `ZZZ: hello` printed `got:fallback`, and `got:hello` once the keys were renamed to sort the other way. The scan now shares one walker with the expander (`walk_var_refs`) and receives both the name the shell reads (`ZZZ`) and the raw reference (`ZZZ:-fallback`); the expander still looks the raw reference up, so a parameter expansion outside a command fails naming the whole reference exactly as `tests/dollar_escape_test.rs` pins. Covers `:-`, `:+`, `#`, `%`, `/`, and `${#NAME}`.
- **The comment on the command environment now describes the environment the command gets** — `src/cfg/env.rs:execute_shell_command_with_env` — `env_clear()` plus seven essentials is immediately overwritten by `cmd.envs(env_overrides)`, which is the whole inherited environment minus the declared keys plus the values resolved so far. The essential list is a floor for exactly one case: when one of those seven names is itself a declared key, and is therefore stripped from the context until it resolves.

### Deviations
- **The comment fix also touched the neighbouring claim in `evaluate_single_env_value`.** Its parenthetical called the same environment "the controlled command environment [that] exists to prevent" a parent-env leak, which is the identical false statement one screen up; the doc bullet only names `:440-452`. Rewritten to say what actually makes the leak reachable (the context this resolves against carries the inherited environment) and the same sentence in the test's doc comment (`src/cfg/env_tests.rs:command_output_is_not_rescanned_for_variable_references`) with it. Behavior unchanged.
- **The failing-command tests count executions with `$$`, not `$RANDOM`.** `/bin/sh` here is dash, where `$RANDOM` expands to the empty string, so every touch would land on one filename and the count could not distinguish one execution from three. `$$` is the shell's PID, unique per `sh -c`, so the marker count *is* the execution count. The doc's literal `$RANDOM` shape was also run against the binary (see below); it passes, it just cannot fail.
- **`a_command_referencing_an_earlier_sibling_still_resolves` and `a_command_referencing_an_inherited_name_resolves_from_the_environment` are green before and after by design.** The first is the declaration order that already worked by luck (the doc asks for both orders, so both are pinned); the second is the `otto-dev` blast-radius pin, whose whole point is that the new rule does *not* change it.

### Tradeoffs
- **The now-unreachable partial-resolution fallback (`env.rs`, after the cycle check) was left in place** vs replacing it with a hard error — every entry in `still_pending` now got there through the deferral rule, so each has a reference to another unresolved declared key, so `find_reference_cycle` cannot return `None` and the fallback cannot run. Deleting it is a behavior claim about a branch nothing exercises; it stays as the fail-closed backstop the comment above `max_iterations` already describes, and the phase does not widen to it.
- **`find_reference_cycle` still follows a self-edge when a value names both itself and a pending sibling** (`A: "$A-$B"`, `B: "$A"` reports the path `A -> A` rather than `A -> B -> A`) vs skipping self-edges there — the verdict is right (it is a real deadlock and it is reported as a cycle) and only the path is imprecise. Out of this phase's bullets; a self-reference alone no longer reaches that branch at all, because it evaluates instead of deferring.

## Phase 4: cfg load-time validation and schema truth

### Design decisions
- **All four `foreach:` load checks are reached through one `ForeachSpec::validate(task_name)`** — `src/cfg/task.rs:ForeachSpec::validate`, called from `src/cli/parser/config.rs:validate_foreach_specs` — the parser's load path should have one foreach seam, not three; `validate_sources`, `validate_var_name` and `validate_range` stay separate functions (and `validate_sources` stays public, because `resolve_command_items` calls it on its own).
- **The source counter reports what it found, not what it forbade** — `src/cfg/task.rs:validate_sources` — `Task 'multi': foreach declares glob and items; foreach takes exactly one source (command, glob, items, or range)`. Zero sources gets its own arm (`foreach declares no source`), which is the `foreach: {}` case that used to load and fail at expansion.
- **The range is counted at load through the same parse the expansion uses** — `src/cfg/task.rs:parse_range`, called by both `validate_range` and `resolve_range` — the doc's bullet put the checked arithmetic in `resolve_range`, but `resolve_range` is not on the load path (the only `--help` caller, `cli/parser/command.rs:23`, swallows its error with `map_or(0, ..)`), so a fix there alone could not satisfy the "fails at load" criterion. `resolve_range` keeps its own copy of the guard for the run path.
- **The overflow arm names `max_items` too** — `src/cfg/task.rs:validate_range` — `checked_add` is the only thing that separates `0-18446744073709551615` from `0-18446744073709551614`, and an author who hits either wants the same sentence: the limit they blew past.
- **`Nargs::Range` stores the counts the ottofile wrote** — `src/cfg/param.rs` `Deserialize`/`Serialize`/`Display`, `src/cli/parser.rs:nargs_to_num_args` — `"3"` is `Range(3, 3)` and `"2:5"` is `Range(2, 5)`. The offset `min` existed only so the serializer could add it back; three readers had to know about it and one of them (the reference page) got it wrong.
- **`otto.jobs` is `Option<usize>` with `skip_serializing_if = "Option::is_none"`** — `src/cfg/otto.rs:OttoSpec` — `default_jobs()` and `is_default_jobs()` are gone; the CPU-count default lives in `cli/parser.rs` (`DEFAULT_JOBS`, clap's default) and the ottofile value now only overrides it when present (`cli/parser.rs`, the `!jobs_explicit` branch). `deserialize_jobs` keeps rejecting `Some(0)`, unchanged in behavior.
- **The three new edge visitors stringify through `EdgeSpec::sugar`** — `src/cfg/edge.rs:EdgeVisitor` — `visit_u64`/`visit_i64`/`visit_bool` produce `from_sugar: true`, so `after: [2024]` re-emits as the bare `2024` it was written as rather than gaining a `{task, when}` map.
  - **2026-09-04 amendment: stringifying the parsed scalar only agrees with the task key when the author wrote the canonical spelling.** The bullet above assumed the edge and the task key are "the same name written in the same place", which holds for `2024` and breaks for every other spelling of the same scalar: the task map reads its key with `next_key::<String>()` and gets the raw source text (`0x1f`), while the edge visitor is handed the resolved integer and can only render `31`. Measured on `af77d6a` with `tasks: {0x1f: {...}, report: {after: [0x1f], ...}}`: `Task '31' not found`, naming a task the author never wrote, where v2.2.1 failed the load pointing at the line. Same divergence for `True`/`after: [True]` and `+5`/`after: [+5]`. yaml_serde hands a visitor no route back to a plain scalar's source text (`de.rs:visit_untagged_scalar` parses before the visitor sees anything), so the two are reconciled after the map is built instead: `src/cfg/task.rs:resolve_scalar_edge_targets`, called at the end of `deserialize_task_map`, rewrites an `after:`/`before:` target that names no task to the one task key it is the resolved form of. The author's spelling is what survives, so `otto 0x1f` still runs the task and re-emit is unchanged; an exact key match always wins, and two keys resolving to one name claim nothing. What it cannot do is tell a quoted key from an unquoted one, because YAML strips the quotes before serde is handed the key: see the open question below.

### Deviations
- **The load-time range check lives in `validate_range`, not only in `resolve_range` (same effect, correct seam).** Reason above; both call `parse_range`, so there is one parser and two callers, not two copies.
- **The private-repo citation was dropped from all six sites in `src/cfg/`, not just `config.rs:12`.** `otto.rs` x2, `task.rs` x2, `param.rs` and `config.rs` all carried the same `Per borg/src/config.rs:281-285` sentence; the doc's stated reason (a private repo path in a public tree) is a property of the string, not of the one file it happened to name. The rule each one states is kept verbatim.
- **`ottofile-reference.md` gained three sentences beyond the `nargs` row the bullet names**: the `foreach` section now states the exactly-one-source rule, the `as` row states the identifier rule, and the `range` row states that the count is checked at load. All three are load errors this phase introduced; leaving them undocumented would have made the page wrong in the same way the `nargs` row was.
- **`tests/config_validation_test.rs` is a new integration file** rather than additions to an existing one: "at load" is the claim under test, and the existing foreach files are organized by feature (`foreach_command_test.rs`, `foreach_jobs_test.rs`), not by lifecycle stage.
- **Two tests were inverted rather than deleted.** `test_foreach_static_sources_still_validate_clean` (`src/cfg/task_tests.rs`) pinned the old "only a `command:` source is exclusive" behavior by name and is now `two_static_foreach_sources_are_rejected_naming_both`, with `exactly_one_static_foreach_source_validates_clean` keeping the positive case. `command_combined_with_a_static_source_is_a_config_error` (`tests/foreach_command_test.rs`) asserted the old message fragment `cannot be combined with items` and now asserts `declares command and items`.
- **`Nargs::Range(0, 3)` in `test_nargs_roundtrip_all_variants` became `Range(3, 3)`.** `Range(0, N)` is no longer a value any ottofile can produce: it serialized to `"0:3"`, which the deserializer rejects (`min must be at least 1`), so the case was asserting a round-trip through a spelling the schema does not accept.

### Tradeoffs
- **`foreach.items` did NOT get a `skip_serializing_if`** vs adding `Vec::is_empty` alongside the other seven — the doc lists the eight fields by name and `items` is not among them; an explicitly written `items: []` is also the one empty source that says something (it is now a load error, and dropping the key on re-emit would change which error the author sees). The minimal-foreach round-trip test passes without it.
- **`resolve_range` keeps its own count guard** vs relying on the load-time check — `resolve_items` is reachable from `TaskSpec::expand_foreach`, which does not go through the parser, so removing it would leave one caller unguarded for the sake of not repeating four lines.
- **`DynamicResolver::has_foreach`/`has_choices` are `#[cfg(test)]`, not deleted** — the doc allows either; they are the only way the memoization tests can distinguish "cached" from "resolved again cheaply", and the production surface they would otherwise need (`foreach_items` with a counting closure) is what those tests already do one level up.

### Open questions
- **The scalar-edge reconciliation binds a quoted key to an edge written as its resolved value, and that is accepted rather than solved.** Raised by the 2026-09-04 review panel as its one must-fix. `tasks: {"0x1f": {...}, report: {after: [31], ...}}` runs both tasks with the edge bound to `"0x1f"`, where v2.2.1 refused the load with `invalid type: integer 31`. The cause is the same one that made the original bug unfixable at the visitor: YAML resolves and unquotes before serde sees anything, so `"0x1f":` and `0x1f:` are the same four bytes by the time `next_key::<String>()` returns, and no signal survives to tell them apart. Reaching it takes a hex, octal, boolean or signed-decimal spelling quoted on one side and written as its resolved value on the other; the panel probed `1.0`, `1e3`, `.5`, `007`, `no` and a path and found none of them rewritten. The alternative is to give up the case authors actually write (`0x1f:` plus `after: [0x1f]`), so this is documented and pinned by `task_tests.rs:a_quoted_scalar_key_is_indistinguishable_from_an_unquoted_one` rather than narrowed. Reopen it only if a real ottofile hits it.
- **`after:` is documented backwards.** `docs/commands/ottofile-reference.md:90` says "Tasks this one runs after", but the scheduler treats the edge the other way: with `report: {after: [alpha]}`, `report` runs FIRST and `alpha` is reported as depending on it (`[alpha] skipped (dep report failed; ...)` when `report` fails). Found while verifying the numeric-edge criterion, which is unaffected (the numeric and string forms behave identically). Not this phase's bullet, and the fix is either a one-line doc correction or a scheduler change, so it needs the author's call. Phases 16 and 17 are the doc phases if it is the former.

## Phase 5: CLI builtin routing

### Design decisions
- **A mixed builtin/user task list is rejected in one pure function, not in the dispatcher** — `src/cli/parser.rs:reject_mixed_task_list`, called from `Parser::parse` right before `process_tasks_with_filter` — the doc puts the fix in `parse` because that is where both task-source paths (explicit args and `otto.tasks` defaults) have converged into one resolved name list, so one call covers both. The function partitions and names every offender on each side, which is what makes the message say `'Clean'` *and* `'build'` rather than one of them.
- **`filter_execution_tasks` deleted rather than kept as a no-op** — `src/app.rs` — with `parse` rejecting the mixed shape, the only task lists that reach `execute_with_terminal_output`/`execute_with_tui` are all-builtin (dispatched by `find_builtin` above it) or all-user, so the filter could only ever be an identity function and the "No tasks to execute" check behind it could only ever be false. Both call sites now pass `tasks` straight into `build_executor_tasks`.
- **Builtin task names are reserved at load, next to the param check** — `src/cli/parser/config.rs:validate_no_builtin_tasks`, called from `load_config_from_path` immediately before `validate_no_builtin_params` — same shape and same wording as the param rejection ("Capitalized names are reserved for otto builtins"), because it is the same class of mistake. Load time, so every surface that reads the ottofile reports it, including `--help` and `--tasks`.
  - **2026-09-04 amendment: the derivation stopped one field short.** Phase 6 derived every builtin's params from its clap `Command` and then took the one-line help `otto --help` lists it with from a second, hand-written string per builtin, so the two renderings of one command could still drift, and three of the six had: `otto --help` said `Clean old runs from ~/.otto/`, `View execution history`, `View execution statistics` where `otto <B> --help` said `Clean old otto run directories`, `Show execution history`, `Show execution statistics`. v2.2.1 disagreed the same way (plus `Convert Makefile to Otto YAML format`), so this is latent drift rather than a regression. `builtin_task` now builds the line as `[built-in] ` plus `Command::get_about`, the tuple in `builtin_clap_commands` is gone, and the `builtins.rs` checklist no longer tells a reader to write a second description. `parser_tests_b.rs:every_builtin_help_line_is_its_clap_about` asserts the equality for all six.
    - **2026-09-05: `every_builtin_help_line_is_its_clap_about` is a reintroduction guard, and its doc comment now says so.** Panel note. The test reads each `about` from the same `builtin_clap_commands()` the production code derives the line from, so it cannot fail while the derivation exists and it asserts nothing about what any builtin's sentence says. That is the right thing to want here (pinning the six sentences literally would recreate the second copy this fix deleted), but a reader was entitled to think it tested more than it does.
  - **2026-09-04 amendment: the reservation reached `Convert` late.** Reserving the names at load without teaching the converter about them made `otto Convert` emit output its own consumer rejects: a Makefile with a `Clean:` target converted at exit 0 (`--strict` silent, since nothing warned) into `tasks: {Clean: ...}`, and `otto -o otto.yml --tasks` then failed with `Task 'Clean' defines reserved builtin command name`. v2.2.1 loaded the same output and ran it. `src/makefile/converter.rs:builtin_renames` now maps every target `is_builtin` reserves to its lowercased spelling (`clean`; `clean-task` when that is taken), applies it to the task key, every `before:` edge and `otto.tasks` through one `task_name` accessor, and warns at the target's line so `--strict` refuses the conversion. `makefiles/builtin-name-target` is the fixture; `tests/makefile_converter_test.rs:test_every_fixture_output_loads_through_otto` runs every fixture's output through the binary, which is the check that would have caught this.
- **`-h` and `-t` interception is gated on a shared "does a task claim this short?" query** — `src/cli/parser/help.rs:args_claim_short`, used by `help_requested_in` (`-h`) and by `Parser::parse`'s `take_tui_flag` call (`-t`) — every single-letter token otto intercepts is a name taken away from the ottofile author, so both interceptions ask the same question in the same way: a task in the arg list that declares the short owns it. Reads declarations only; resolves nothing and runs nothing, so it is safe on the help path.
  - **2026-09-04 amendment: the shared query could not see a foreach subtask's parent.** `args_claim_short` looked each token up as an exact key of the task map, and a subtask is addressed as `up:gamma`, which is not a key, so the answer was "no task claims this" for every subtask and the parent lost the short the moment the user addressed one of its items. `value_taking_options` (`src/cli/parser/discovery.rs`) had the mapping right from the start (`parent_task_name` -> `naming::parent_or_self`); this one place did not. Measured against a `foreach` task `up` declaring `-t|--target`: `otto up:gamma -t x` ran on v2.2.1 (`[up:gamma] up gamma target=x`) and on `26bafc6` failed with clap's `unexpected argument 'x' found`, because `-t` was stripped as the TUI flag and `x` was left a stray positional. With `-h|--host` instead, `otto up:gamma -h example.com` printed help and then `Task 'up:gamma' not found` on both v2.2.1 and `26bafc6`, so that half is a latent bug the same lookup fixes. `args_claim_short` now resolves through `crate::naming::parent_or_self`, which reaches both interceptions (`take_tui_flag`'s `take_short` and `help_requested_in`). `parser_tests_a.rs:a_foreach_subtask_claims_its_parents_short_t` and `..._short_h` pin them.
- **`has_user_tasks()` replaces four `tasks.is_empty()` checks** — `src/cli/parser/help.rs:has_user_tasks`, used by `should_show_help` and `build_help_command` — `inject_builtin_commands` runs before every help decision, so the task map always holds at least the six builtins and `is_empty()` was a question with a constant answer.

- **The `builtins.rs` checklist now names the five real lists** — `src/cli/builtins.rs` — it pointed at `inject_NAME_meta_task() in parser.rs` (that file is now `parser/meta_tasks.rs`), omitted the `Builtin` enum and the `main.rs` route entirely, and told the reader to "add an execution filter", which is exactly the mechanism this phase deleted.

### Deviations
- **The `-h` bullet also needed a change in `task_to_command`, not just in the help gate** — `src/cli/parser/command.rs` — with only the help-gate fix, a task declaring `-h|--host` still could not be given a host: clap asserts on the duplicate short outright (`Command build: Short option names must be unique for each argument, but '-h' is in use by both 'host' and 'help'`), which panicked the binary on *every* invocation of that task, `--host` included. Reproduced on `f9882ed` before touching anything. The task's command now disables clap's auto help flag and re-adds a long-only `--help` when a param claims `-h`, so `otto build -h example.com` binds and `otto build --help` still renders help. Same effect the bullet asks for, at the seam that makes it reachable.
- **`-t` is stripped only when no task in the arg list declares `-t` itself** — `src/cli/parser.rs:take_tui_flag` now takes a `take_short` argument. The bullet says "strip `-t` as well as `--tui`" unconditionally; done unconditionally it would create the exact bug the `-h` bullet two lines below it exists to fix, and would break `otto History -t <task>`, whose meta task declares `-t/--task` today (the doc's own Phase 6 text says so). `--tui` is stripped unconditionally, as before: a task cannot declare a long that collides with a global.
- **The "no ottofile found" epilogue is now gated on `self.ottofile.is_none()`, not on the task map being empty** — `src/cli/parser/command.rs:build_help_command` — swapping `tasks.is_empty()` for `has_user_tasks()` as written would have printed "ERROR: No ottofile found in this directory or any parent directory!" for an ottofile that exists and declares no tasks of its own, which is the case the bullet is about. The task/builtin subcommand loops are now unconditional (they iterate an empty map harmlessly) and only the epilogue is conditional.
- **The mixed-list guard does not reject two builtins named together** — `otto Clean Stats` still runs `Clean` and drops `Stats`, because the doc's rule is specifically "a builtin and a user task". Left as specified; listed under open questions.

### Tradeoffs
- **Rejecting a mixed list in `parse` vs making `find_builtin` return an error** — the error belongs where the user's words are still visible: `parse` holds the resolved *name* list, so the message quotes what was typed. `find_builtin` sees `Vec<Task>` after DAG construction, and it is also the wrong layer to fail from, since both output modes call it after they have already printed nothing.
- **Applying the mixed-list guard to `otto.tasks` defaults too** vs only to explicitly typed args — one call site, one rule, and an ottofile whose defaults are `[Clean, build]` is unrunnable for the same reason `otto Clean build` is. Cost: that ottofile now fails at run rather than silently running `Clean`. `*` expansion already excludes builtins, so the common shape is unaffected.
- **A separate `EarlyCommand` enum in `main.rs`** vs a method on `otto::app::Builtin` — the early-route set is deliberately not the builtin set, and a `Builtin::early_route()` returning `Option` would put "except Graph" back into a comment inside the library, away from the `main.rs` match it constrains.
- **`args_claim_short` scans the arg list for known task names** vs partitioning first — partitioning needs `get_task_names`, which can resolve a command-sourced `foreach`, i.e. run user code. The help path must execute nothing, so this reads the params map directly and accepts being coarse: a task declaring `-t` anywhere in the invocation suppresses otto's `-t` for the whole invocation.
- **`disable_help_flag` + a long-only `--help`** vs `mut_arg`-ing clap's help short away — `disable_help_flag` is the API clap's own assertion message recommends, and it is skipped entirely when a param already declares a long `--help`, so the re-add can never itself collide.

## Phase 8: Upgrade

### Design decisions
- **Rollback picks the newest backup whose version is strictly OLDER than the version running now** — `src/cli/commands/upgrade.rs:select_rollback_target`, a free function so it is unit-testable without a filesystem — the safety backup a rollback writes is always the newest file in the directory when the next rollback runs, so "newest wins" made two rollbacks undo each other and no run of rollbacks ever reached the version before last. See Deviations: "differs from `current_version()`", the doc's literal rule, does not achieve this.
  - **2026-09-04 amendment: "older" was decided by `Version::parse`, which reads a dev build as a prerelease of the tag it descends from.** `build.rs` records `git describe --tags --always`, so a build past the last tag calls itself `v2.2.1-28-ga443ad7`, and semver reads that suffix as a PRERELEASE of 2.2.1, sorting it BELOW the release. Every ordering in `upgrade.rs` inverted for a dev build. Measured with `Upgrade --dry-run` against the real release API from this checkout: v2.2.1 (a tagged build) printed `You are already on the target version!`; `a443ad7` printed `Current version: v2.2.1-28-ga443ad7 / Target version: v2.2.1` and then planned the install, calling a downgrade an upgrade; fixed prints `Current version is newer than target version. / Use --force to downgrade.` Rollback inverted the same way, treating a backup 28 commits newer than the running version as a rollback candidate. `parse_build_version` now splits a `-<n>-g<sha>` suffix off the release core and orders on `(release, commits)`, so a build past a tag is newer than that tag and older than the next one; a genuine prerelease tag (`v2.3.0-rc.1`) has no such suffix and keeps semver's ordering; and a bare sha, which `--always` prints when no tag is reachable, is refused with a sentence naming where the string came from instead of semver's `unexpected character`. Used by the upgrade compare and by `select_rollback_target`. `current_version()` still returns the describe string unchanged: what it feeds is display, and printing `v2.2.1-28-ga443ad7` is the honest answer to what is running. Latent bug, not a regression: the compare predates this branch. The rollback selection it also corrupts is new here.
  - **2026-09-04 amendment: the `--dry-run` plan listed the steps in an order the real run does not use.** `execute_upgrade` calls `download_and_check_checksum` and only then `create_backup`, while `dry_run_steps` printed `Create backup` as step 2 and the checksum as step 3, so a reader who hit a checksum failure went looking for a backup that is never written (nothing is backed up until the download verifies). Measured with `Upgrade --dry-run --force`: `2cfad9e` prints `2. Create backup ... / 3. Check the download against the release's published .sha256 checksum`; fixed prints the checksum as 2 and the backup as 3. v2.2.1 has no checksum step at all, that verification being new to this branch, so this is latent within the branch rather than a regression against the release. `upgrade_tests.rs:the_dry_run_plan_checks_the_checksum_before_it_makes_a_backup` pins the order by position rather than by exact wording.
- **A backup whose version is not a semver is skipped, not guessed at** — same function — `~/.otto/backups` (or `--backup-dir`) is a directory anything can write into, and a version that cannot be ordered cannot be shown to be older than this one. `list_backups_tolerates_adversarial_filenames` already establishes that the parser accepts odd names; this decides what selection does with them.
- **`current_version` joined `api_base` and `install_target` as an `#[arg(skip)]` field with a `#[cfg(test)]` writer** — `src/cli/commands/upgrade.rs:UpgradeCommand`, written only by `with_current_version` — a process's own version is `GIT_DESCRIBE`, fixed at build time, so "roll back twice" (two processes at two versions) cannot be expressed any other way. The field carries the same "no `env =`, no user-settable writer" doc as the other two.
- **The releases override became an API base, not a releases URL** — `api_base` plus `releases_url()`, `latest_release_url()`, `tagged_release_url()` — one string now yields all three endpoints, so a fixture server and production compose the same paths. This is also what makes the phase's grep criterion land on real code rather than a comment.
- **One `get_json<T>` behind `fetch_release` and `fetch_releases`** — same file — the status check and the `Authorization` header live in one place, so a 404 from `/releases/tags/vX` reports the same way as one from `/releases` instead of being parsed as a release.
- **`dry_run_steps` and `version_lines` return data; the printers print it** — same file — the phase's criteria are about what those two surfaces *say* (the asset name, the step numbers, which release is marked latest), and asserting on stdout in-process is not a thing this repo does. The numbering is now the position in a `Vec`, so `--no-backup` cannot reintroduce a gap.
- **`make_executable` is its own function and `stage_beside_with` injects it** — same file — the discard-on-failure path needs a chmod that fails on a file this process just created, which no test can arrange from the outside; the file already establishes the injected-parameter pattern with `verify_binary_within` and `download_with_progress_within`, both documented the same way.
- **`get_backup_dir` goes through `layout::resolve_otto_home()`** — same file — `$OTTO_HOME` moves every other piece of otto's state and backups were the one directory that rebuilt `$HOME/.otto` itself. Verified against the real binary: `OTTO_HOME=/tmp/.../ottohome otto Upgrade --dry-run` plans its backup under `/tmp/.../ottohome/backups`.

### Deviations
- **The rollback rule is "strictly older", not the doc's "differs from `current_version()`" (same intent, correct rule).** Walked through: start on 3.0.0 with backups 2.0.0 and 1.0.0. Rollback 1 installs 2.0.0 and writes a safety backup of 3.0.0, now the newest file. Rollback 2 runs as 2.0.0, and the newest backup whose version *differs* from 2.0.0 is that 3.0.0 safety backup: the doc's rule rolls forward onto the version just left and fails the doc's own test bullet ("rollback twice across three fixture versions lands on the oldest"). "Older than the version running now" satisfies both, subsumes "differs", and makes repeated rollback monotonic.
- **`download_and_verify` was renamed to `download_and_check_checksum`.** The bullet says the *messages* must not read as signature verification; a function name is the message a reader hits first, and this one claimed the stronger thing. Its doc now states in so many words that a checksum match says nothing about who produced either file. Three test names renamed with it.
- **`--list-versions` was fixed too, which the bullet does not name.** Its "(latest)" marker was `i == 0` over `/releases`, i.e. the same "newest created is latest" assumption the bullet removes from the upgrade path; leaving it would have left the file asserting two different meanings of "latest" one screen apart. It now marks the tag `/releases/latest` returns, and warns and drops the marker if that lookup fails rather than failing a listing.
- **The `--dry-run` plan gained a step it always performed.** The checksum check happens between download and extract and the plan never mentioned it; with the numbering rebuilt anyway, omitting it would have been a second wrong plan.
- **`test_platform_detection` was deleted, not rewritten.** It existed to read `platform._os`, one of the fields this phase deletes; `platform_strings_match_the_published_asset_suffixes` already asserts the detected suffix is one `install.sh` publishes, which is strictly stronger.
- **`test_backup_dir_default` was rewritten rather than left alone.** It asserted `.otto/backups` is a substring of the default, which stays true under a rebuilt `$HOME/.otto` and so could not see the fix; it now pins both branches (`$OTTO_HOME` set, and unset) and is `#[serial]` because the environment is process-global and other tests in this binary write `OTTO_HOME`.
- **`grep -n 'releases/latest'` prints one hit only because two doc comments were reworded** to name the accessor functions instead of respelling the path. The remaining hit is the production `format!`.

### Tradeoffs
- **`select_rollback_target` fails loudly when nothing older exists** vs falling back to the newest backup — a rollback that reinstalls the version already running is a no-op reported as success. The error names the current version and lists the versions present, so the answer to "why did it refuse" is in the message.
- **The safety backup is skipped when a backup of the current version already exists** vs always writing one — a second copy of the same bytes under a newer timestamp is what created the trap in the first place, and it is not additional safety. Cost: if the installed binary at that version has been modified since its backup was taken, the modification is not preserved. Rollback restores released binaries, so that case is a user who overwrote `otto` by hand.
- **`--version X` now resolves before the already-on-target and downgrade short-circuits.** `otto Upgrade --version <nonexistent>` used to print "Use --force to downgrade" and exit 0 when the current version was newer; it now fails naming the version. Same number of HTTP requests, and the honest answer is that the release does not exist.
- **`stage_beside_with` takes a closure that production never varies** vs leaving the discard path untested — the alternative was a `#[cfg(test)]` fault-injection global, which is worse, or no test, which is how the stranding shipped.

## Phase 9: State correctness

### Design decisions
- **`TransactionGuard` lives in `state/db.rs`, `pub(super)`** — `src/executor/state/db.rs` — the doc offered `state/mod.rs` or `db.rs`; `db.rs` already owns every other piece of connection-level plumbing (busy timeout, WAL retry, `with_connection`), and `mod.rs` is a twelve-line re-export list. Its doc comment is now the single place that explains why immediate and not deferred, so neither `migrations.rs` nor `manager.rs` has to restate it.
- **One `migrate_step(conn, target, step)` wraps all four upgrade branches** — `migrations.rs:migrate_step` — the immediate transaction, the version re-read, the step, and the version bump are one shape used four times rather than four hand-written copies that already drifted once (the v0 branch had a transaction and the reasoning; the upgrade branches had neither).
- **`delete_run` is split into `read_run_with_project` and `resolve_run_directory`** — `manager.rs` — the ordering requirement (resolve and fence before `BEGIN`, unlink after `COMMIT`) needs the row *before* the transaction that deletes it, and the fence is a fallible step that must not run inside the write lock. `resolve_run_directory` returns `Option<PathBuf>`: `None` means nothing on disk (logged), `Some` means canonical and checked. The transaction re-reads the row's existence under the write lock so a concurrent delete cannot double-decrement `run_count`.
- **The hostname comes from `RunMetadata::current_system_info()`, the user still comes from `ExecutionContext`** — `workspace.rs:record_run_start_in_db` — the helper returns both, but `context.user` is resolved once at run start and is what `run.yaml` serializes; taking the user from the helper too would have let the two disagree if `$USER` changed mid-run.
- **`MemoryStateStore::get_all_task_stats` drops its read guard before the loop** — `ports/db.rs` — it called `get_task_stats`, which takes the same `RwLock` read side again; `std::sync::RwLock` is not reentrant when a writer is queued. Not a doc bullet, but the parity test this phase adds calls that method, and a deadlock there would have looked like a hung test.
- **`bad_column(13, ...)` for an unknown `skip_kind`** — `manager.rs:row_to_task_record` — same index-and-message shape as the `status` column beside it, so a corrupt row reports which column is corrupt.

### Deviations
- **`record_task_complete`'s clamp is `MAX(?3 - started_at, 0)` inside a `CASE`, not the doc's bare `CASE WHEN started_at IS NULL THEN NULL ELSE MAX(?3 - started_at, 0) END`** — that is what the doc asked for; noted only because the parameter numbering changed with it (`?4` is now `task_id`, the old `?4` duration parameter is gone).
- **`delete_run` reads the run row twice: once before `BEGIN`, once (as a `COUNT(*)`) inside it.** The doc says "resolve and validate the path before `BEGIN`", which requires the row outside the transaction, and correctness requires knowing inside the transaction that the row is still there. The second read is a count, not a full row map.
- **A new integration test file, `tests/history_records_the_run_test.rs`, carries the end-to-end half of the `hostname` and `script_hash` bullets.** The doc's success criteria name a `manager_tests.rs` assertion for `script_hash`; that test exists, but it can only prove the column round-trips, because `record_task_start` takes the hash as a parameter. The production defect was the *caller* passing `None`, so the caller is what the new file exercises: a real run, then `otto History --json`.
- **`test_migrate_v4_to_v5_preserves_rows_and_task_links` also asserts foreign keys are back ON afterwards.** Turning them ON as the doc asks makes the `PRAGMA foreign_keys=OFF` toggle load-bearing; asserting the restore is what makes the *other half* of the toggle load-bearing, and it was not covered anywhere.
- **`db_tests.rs`'s `clear_path_env` became `with_path_env` plus a `swap_var` primitive, and a test asserts the restore.** The doc says to use `manager_tests`'s `with_otto_home` shape; two knobs and three call sites made a two-argument version cleaner than two nested helpers.

### Tradeoffs
- **Fault injection with SQL triggers** vs a `#[cfg(test)]` failure hook in the store — the two transactions this phase adds can only be proven by making a statement in the middle of them fail, and a `BEFORE INSERT ... RAISE(ABORT)` trigger does that from the test with no production code touched. Cost: the tests know a little SQL about the schema they are testing.
- **The concurrent-upgrade test writes its v4 fixture with `rusqlite` directly** vs shipping a binary `.db` fixture or exposing a downgrade helper — otto can only ever produce the current schema, so the fixture has to be written by hand somewhere. Inline DDL in the test is greppable and diffs cleanly; a checked-in binary fixture does neither. `rusqlite` needed no Cargo change: cargo already passes `[dependencies]` to integration-test targets.
- **The task-stats parity test uses sub-second durations, so both backends land on `Some(0.0)`** vs forcing distinct durations — forcing them means either sleeping (slow, flaky) or reaching into the private connection from a module that cannot see it. `Some(0.0)` versus `None` is exactly the defect, and it is deterministic.
- **`get_task_stats`'s avg/min/max are computed in a second pass over a per-project duration map** vs threading a running total through the first pass — the map is 8 lines and mirrors `AVG`/`MIN`/`MAX`'s "over the rows that have a value" semantics without an is-first special case.

### Design decisions
- **`FileSystem` trait trimmed from 25 methods to 15** — `src/ports/fs.rs` — removed async `is_file`, `metadata`, `remove_file`, `remove_dir_all`, `copy`, `read_dir`, `read_link`, `symlink`, `set_permissions`, and sync `metadata_sync`, plus `RealFs`/`MemFs`'s implementations of each. - **`Workspace::script_cache` deleted** — `src/executor/workspace.rs` — its only callers were its own two tests (`workspace_tests.rs`); the real cache path is `Workspace::cache_dir().join(...)`, built inline at `action.rs:write_script`. The test at `test_relative_script_cache_path` now builds its input path directly (`ws.cache_dir().join("hash123.sh")`) instead of through the deleted method.
- **`get_recent_runs`/`get_run_tasks` removed from the `StateStore` trait and both backends** — `src/ports/db.rs`, `src/executor/state/manager.rs` — `grep -rn 'fn get_run_tasks(\|fn get_recent_runs('` across `src/` (excluding test files) showed no caller but the trait's own forwarding impl. `get_recent_runs(limit, filter)` is byte-for-byte `get_runs_with_filters(None, filter, limit)`; every test call site was mechanically rewritten to call that instead. `get_run_tasks` has no equivalent production entry point (nothing reads "every task in one run" outside a test), so it could not be redirected the same way.
- **`get_run_tasks`'s query moved into two test-only helper functions named `run_tasks`, one per backend** — `src/executor/state/manager_tests.rs` (raw SQL against `manager.db`, reusing the private `StateManager::row_to_task_record` mapper) and `src/ports/db_tests.rs` (reads `MemoryStateStore`'s private `tasks` field directly). Both are reachable only because the test module is a descendant of the module that owns the private items it touches. The two `tests/silent_success_test.rs` call sites are an external integration-test binary and cannot reach either helper, so they were redirected to `get_task_history(name, 1)` instead, which is equivalent given each of those two tests only ever populates one run.
- **`get_task_stats`/`get_all_task_stats` rewritten as one `GROUP BY` query each** — `src/executor/state/manager.rs` — replaced the `SELECT DISTINCT` project/task list plus eight follow-up queries per row with a single query returning `COUNT(*)`, three `SUM(status = '...')` boolean-sum counts, `AVG`/`MIN`/`MAX(duration_seconds)`, and `MAX(started_at)`, grouped by project (or by task+project for the all-tasks query). `last_status` is the one field a plain aggregate cannot hand back correlated to the group, since the query already has two other `MIN`/`MAX` aggregates in play (SQLite's bare-column-follows-the-max-row extension only applies with exactly one `min()`/`max()` in the query); it stays a correlated scalar subquery, now one per group instead of one query per (project, task) pair for every other field. `get_all_task_stats`'s `LIMIT` binds `-1` for "no limit" (SQLite's own spelling) instead of building two query strings.
- **One `project_name_from(ottofile: Option<&Path>, hash: &str) -> String` in `src/naming.rs`** — replaced the three copies at `StateManager::ensure_project`, `schema::migrate_v1_to_v2`'s name backfill, and `MemoryStateStore::get_or_create_project`. Placed in the existing top-level `naming.rs` rather than a new module under `executor/state`, matching the doc's instruction and that module's existing role as "the one place that knows how a name is derived."
- **`RUNS_TABLE_COLUMNS` replaces `RUNS_TABLE_DDL`** — `src/executor/state/schema.rs` — the old constant was a complete `CREATE TABLE IF NOT EXISTS runs (...)` statement, unusable for `runs_v5` (different table name, no `IF NOT EXISTS`). The new constant holds only the column list; `init_schema` and `migrate_v4_to_v5` each wrap it with `format!` for their own table name and existence clause, so both sides of "cannot drift apart" go through one string.
- **`health_check`, `stats`, `DatabaseStats`, `path()` deleted from `DatabaseManager`** — `src/executor/state/db.rs` — `grep -rn 'health_check\|DatabaseStats\|DatabaseManager'` across `src`/`tests` showed callers only in `db_tests.rs`; `path()` had no caller anywhere, not even in tests. `db.db_path` became a write-only field once `path()` was gone, so the field itself is deleted too (kept, it would have failed `cargo clippy`'s deny-warnings dead-code lint).
- **`DatabaseManager::conn` is `Mutex<Connection>`, not `Arc<Mutex<Connection>>`** — `src/executor/state/db.rs` — nothing ever cloned the `Arc`; `DatabaseManager` itself has no `Clone` impl, and every caller that needs to share state wraps a `StateManager` (or `Arc<dyn StateStore>`) at a higher level.
- **"Where the database lives" doc block moved onto `default_db_path`** — `src/executor/state/db.rs` — it was attached to `refuse_the_developers_real_database`'s `#[cfg(test)]` guard instead of the function it actually documents.

Both comments now say what the type and function actually are.

### Deviations
- **`get_run_tasks` is not simply deleted with its test callers dropped; it survives as two non-public, differently-implemented test helpers.** The doc says "delete `get_run_tasks`" with no redirect noted (unlike `get_recent_runs`, whose redirect target it names explicitly). Taken literally, that would have deleted roughly 40 test assertions across `manager_tests.rs`, `db_tests.rs`, `workspace_tests.rs`, `clean_tests.rs`, and two integration tests, with nothing to replace the coverage they gave (whether a run's task rows round-trip correctly), because the query "every task in one run" has no other production entry point to redirect to. Same effect on the port (no `StateStore` method reachable from production code), but the verification capability is kept rather than deleted outright. Recorded here because it is the one place this phase's execution differs from the bullet's literal text rather than filling in a gap the text left open.
- **`schema.rs`'s success criterion for `RUNS_TABLE_DDL` isn't in the phase's grep list.** The doc's Phase 10 success criteria enumerate checks for the `FileSystem` trim, `get_recent_runs`/`health_check`/`script_cache`, and the `otto Stats` byte-identity, but not one for the DDL-sharing bullet. Implemented anyway, since the bullet itself is unambiguous; verified by reading the diff and by `otto ci`'s full migration test suite passing (`migrate_v4_to_v5`'s tests exercise the rebuilt `runs_v5` table shape).

### Tradeoffs
- **`get_task_stats`/`get_all_task_stats`'s `last_status` as a correlated subquery** vs a second bare `MAX`/`MIN`-style aggregate trick — SQLite's "bare column takes the value from the min/max row" extension needs *exactly one* `min()`/`max()` aggregate in the query, and this query already has two (`MIN`/`MAX(duration_seconds)`) plus a third (`MAX(started_at)`) doing double duty as both the aggregate and the value needed. A subquery is one extra index-backed lookup per output row instead of a fragile dependency on which aggregate SQLite's optimizer treats as *the* one.
- **`ORDER BY COUNT(*) DESC, t.name ASC, p.id ASC` in `get_all_task_stats`** vs relying on `GROUP BY`'s natural row order for ties — the old `SELECT DISTINCT` query happened to tie-break alphabetically by task name (observed directly: a fixture with five same-count tasks rendered `final, task1, task2, task3, task4`), because `DISTINCT`'s dedup sorts by its leftmost selected column. That was never a documented guarantee, just a `DISTINCT` implementation detail. An explicit tie-break reproduces it deterministically regardless of what query plan SQLite's optimizer picks for a `GROUP BY`, rather than hoping the accident survives the rewrite.
- **Byte-identity verified against one fixture DB read twice, not two fixture DBs built independently** — real task durations come from real `sleep` commands under actual OS scheduling, so two separate `hello-world`/`parallel-tasks` runs land on the same *shape* but not always the same seconds (observed: one run's `task1` took 4.0s, a rebuilt run's took 3.0s, both legitimate `sleep 2` plus `sleep 1` under load). Running the pre-rewrite and post-rewrite binaries' `Stats`/`Stats --json` against the identical already-populated database file removes that noise entirely and is the stronger proof: it shows the query rewrite changes nothing about how the same rows are reported, which is what the criterion is actually asking.

## Phase 11: Executor cleanup

### Design decisions
- **The blocked-task sweep is one async method plus one pure function, not one function** — `src/executor/scheduler/support.rs::TaskScheduler::sweep_blocked` and `partition_blocked` — the doc asks for one `sweep_blocked(...) -> Vec<Task>` used by all four sites. The classification (which blocked tasks are now ready, which are now unreachable, which stay blocked) is pure and needs nothing but the terminal sets; applying the result needs `&self`, `mark_skipped`, the replay cursor and the `completed_tasks` counter, all of which are async and stateful. Splitting them at that seam is what lets `test_the_blocked_sweep_reads_the_edge_condition_not_bare_completion` assert the rule directly, with no workspace, database or cursor in the test.
- **`sweep_blocked` returns `bool` ("did anything move"), not the swept tasks** — the caller cannot do anything with the tasks: ready ones belong on the queue and unreachable ones have already been marked skipped by the time the call returns. The one thing a caller actually asks is the deadlock question at `scheduler.rs`'s `active_tasks.is_empty()` branch: nothing moved and the ready queue is empty, so the run is finished. The other three call sites ignore the value.
- **The fourth site's `when:`-blindness was the bug, so the folded version classifies gates there too** — `src/executor/scheduler/support.rs::try_start_ready_task` — the up-to-date-skip path used to walk `blocked_task.task_deps.iter().all(|d| completed_set.contains(&d.task))`, which reads a dep's membership and never its edge condition, and had no unreachable branch at all. It now runs the same sweep as the drain loop.
- **`needs_rebuild` returns `bool`** — `src/executor/scheduler/support.rs` — its `Err` was unreachable (`get_file_timestamps` swallowed every error into `None` and always returned `Ok`), and the caller's `Err` arm was a copy of its `Ok(true)` arm: broadcast Started, log, `execute_task`. `get_file_timestamps` drops its `Result` too, with a doc sentence saying why a missing timestamp is not an error: an unknown mtime already means "run the task".
- **`try_start_ready_task`'s three-arm `match` became an `if`/`else`** — deleting the `Err` arm left `Ok(true)`/`Ok(false)`, which is a boolean.
- **`TaskReport::exit_code` and `TaskFailure::exit_code` deleted** — `src/executor/scheduler.rs` — both drain-loop arms destructured with `..` and never read the field, and all three `From` impls set `TaskFailure::exit_code` to `None`, so `code.or(exit_code)` at the report site was always `exit_code`. The body's own `exit_code` local is what the database write already uses, and it is in scope on the single report path. The `..` rest patterns in both drain arms are gone as well: with the field removed, the arms bind every field.
- **`test_try_new_graceful_failure` is now `#[serial]`** — `src/executor/state/manager_tests.rs` — see Deviations; this is not a Phase 11 bullet.

### Deviations
- **`sweep_blocked(...) -> bool` + `partition_blocked(...) -> Swept`, not `sweep_blocked(...) -> Vec<Task>`** — same effect at the correct seam (see Design decisions). One `Vec<Task>` cannot carry a sweep's two outcomes, and the three drain-loop sites need both applied plus the "did anything move" answer.
- **`test_file_dependency_check_error_handling` is renamed and rewritten rather than deleted** — `src/executor/scheduler_tests_b.rs::test_an_unreadable_file_dependency_runs_the_task` — the doc offers "delete or rename". It is now a real assertion: the old body created no output file, so `needs_rebuild` returned at the "output does not exist" check and never looked at the unreadable input path at all. The new body writes the output file first, which forces the timestamp comparison against an input under `/dev/null/` that has no timestamp to give, and asserts the task runs rather than being skipped as up to date.
- **`src/executor/state/manager_tests.rs::test_try_new_graceful_failure` gained `#[serial]`, which belongs to no Phase 11 bullet.** It is a Phase 9 test that reads and writes the process-global `OTTO_HOME` through `with_otto_home` (whose own safety comment claims it is "serialized against every other test that reads the environment") but was not in the `#[serial]` group. Under `otto ci` it failed: `try_new must have created its database under the OTTO_HOME it was given` (`manager_tests.rs:586`), because a concurrent `#[serial]` test's `set_var` landed between this test's `set_var` and its assertion. This phase's new `test_an_up_to_date_skip_marks_its_unreachable_dependents` is one more `#[serial]` `OTTO_HOME` writer, so it made a pre-existing race more likely to fire. Fixed at the root (the missing attribute) rather than by working around it in the new test; five consecutive `cargo test --lib` runs are green afterwards.
- **The doc's claim that the fourth sweep site "never detects newly-unreachable dependents" is accurate, but the divergence was latent rather than observable.** A dependent the fourth site wrongly pushed onto the ready queue was re-classified by the dispatch gate (`scheduler.rs:1497`) before launch and skipped there with the same `skip_record_for` record, and a dependent it wrongly left blocked was picked up by the next drain-loop sweep, which always runs (the `active_tasks.is_empty()` branch, otherwise a report arm). So no end state was wrong; what was wrong is that one of four copies of the rule read the run's state through a different question. Recorded because "prove the fix by reverting it" has a specific answer here: the red test is the unit test on the rule (`partition_blocked` with the deleted site's bare-completion walk restored fails with `left: [] right: ["on_failure"]`), not an end-to-end run.

### Tradeoffs
- **`#[allow(clippy::too_many_arguments)]` on `sweep_blocked`** vs bundling the run's mutable state into a struct — eight parameters, matching its only neighbour `try_start_ready_task`, which carries the same allow for the same reason. A `RunState` struct holding `&mut` borrows of five locals would have to be rebuilt at each of the four call sites or thread a lifetime through the whole drain loop; the shape of `execute_all`'s locals is not this phase's subject.

## Phase 12: Makefile converter truth

### Design decisions
- **The prefix loop lives in `OttoConverter::build_bash_action`** (`src/makefile/converter.rs`) as a `loop` peeling `@`/`-`/`+` from the front of each command line, in any order and any repetition, tracking one `ignore_errors: bool` set by any `-` seen. The old code was an `if`/`else if` that inspected only the first character, so `@-rm -rf dist` kept a literal `-` in the emitted command (no `|| true`) and `-@echo hi` kept a literal `@` for bash to choke on. `+` (make's "always run this line, even under `-n`") has no otto equivalent — there is no dry-run mode to override — so it is simply stripped, same as `@`.
- **The target-name make-expansion check in `MakefileParser::parse_rule`** (`src/makefile/parser.rs`) is placed immediately before the existing pattern-rule (`%`) check and shares its shape: warn naming the target, advance past the header line, call `skip_recipe`, return `Ok(None)`. `converter.rs:228` already warns when a *dependency* contains `$`; the target-name case had no equivalent at all, so a `$(TARGETS): dep` rule quietly became a task literally named `$(TARGETS)` and (being first in the file) the default task.
  - **2026-09-04 amendment: the guard could not fire on a substitution reference, because the split ran first.** `parse_rule` took the rule's colon to be the first `:` in the line, and `$(SRCS:.c=.o): headers` has one inside the expansion, so the target became `$(SRCS` and the dependency list `.c=.o): headers`. That list contains an `=`, so `is_target_specific_variable` matched and the rule was dropped with `target-specific variable on `$(SRCS` is not supported`, its recipe orphaned as `recipe line does not belong to any rule`, and the make-expansion guard never saw a `$(` to warn about. Contrary to the finding that raised this, v2.2.1 was wrong the same way: measured on `$(SRCS:.c=.o): headers` plus a recipe, v2.2.1 and `85bb8fb` both emit the two mis-split warnings and no task, so this is a latent bug, not a regression. `MakefileParser::rule_colon` now scans for the first colon at nesting depth zero, tracking `$(`/`${`, and the existing guard reports `target `$(SRCS:.c=.o)` is a make expansion; otto task names cannot be computed; the rule is skipped`. `makefiles/substitution-ref-target` is the fixture, covering the substitution reference and the `$(OBJS:%.o=%.d)` shape that defeated the `%` pattern-rule guard the same way; reverting `rule_colon` to `find(':')` turns `test_every_fixture_produces_exactly_its_expected_warnings` red.
  - **2026-09-04 amendment, second pass, closed 2026-09-05: the fix covered the TARGET side only; the dependency side is now fixed too.** Raised by the review panel against `a443ad7`, whose subject claims the class rather than the side. `deps.d: $(OBJS:%.o=%.d)` was dropped as `static pattern rule 'deps.d' is not supported` on v2.2.1 and on the fixed tree alike, because `rule_colon` got the depth scan and the `dep_part.contains(':')` test beside it did not. It was left alone on 2026-09-04 for a measured reason: with the rule no longer skipped, `convert_target_to_task` emitted `before: ['$(OBJS:%.o=%.d)']` and every run of the output died with `unknown dependency`, so the one-line fix traded a skipped rule for an unrunnable ottofile. That blocker is gone as of the commit above, which drops the edge for an expansion, so the dependency side now asks `rule_colon` too: only a top-level colon makes a third field. Measured: v2.2.1 skips the rule; fixed converts it, warns that the prerequisite is an expansion, and `otto deps.d` runs. A genuine static pattern rule (`objs: %.o: %.c`) is still rejected. `makefiles/expansion-dependency` carries the case; reverting either half turns `test_every_fixture_matches_its_expected_output` red.
  - **2026-09-05: an expansion that is never closed is now its own message, and `$$` is deliberately NOT skipped.** Two edges of `rule_colon` raised on 2026-09-04 as known and unfixtured. First, `$(BAD: headers` swallows the rest of the line, colon included, so the scan found no top-level colon and the line was reported as `unrecognized line ignored` with its recipe then reported as belonging to no rule: two messages, neither naming the missing paren (v2.2.1 was worse still, emitting a task literally named `$(SRCS`). `rule_colon` now returns `RuleColon::{At, Missing, Unclosed}` and the unclosed case warns `unclosed `$(` or `${` in `<line>`; the rule is skipped`, skipping the recipe with the rule it belongs to. Second, skipping `$$` (make's escaped dollar) before the depth scan was instructed and then measured and NOT done, because it is a regression: `$$` outside a paren already has no effect on the scan (the scan only reacts to `$` immediately followed by `(` or `{`), and skipping it turns `$$(a:b): dep` from a correct `target `$$(a:b)` is a make expansion` into a mis-split `static pattern rule `$$(a``, which is the exact class of bug this scan was written to fix. `makefiles/substitution-ref-target` carries the unclosed case; reverting the `Unclosed` arm turns `test_every_fixture_produces_exactly_its_expected_warnings` red.
  - **2026-09-05: the pre-existing bug that blocked the dependency side is fixed, so the dependency side is no longer blocked.** Recorded on 2026-09-04 as "not this branch's to fix" and then reopened on instruction. Any Makefile with a `$(VAR)` prerequisite converted at exit 0 into an ottofile that could not run: `convert_target_to_task` warned `dependency '$(OBJS)' of 'link' is a make expansion; otto task names cannot be computed` and then emitted the edge anyway, so `otto link` died with `Task 'link' has unknown dependency '$(OBJS)'`. ## Phase 13: TUI

### Design decisions
- **The render window is measured in wrapped rows, not buffer lines** — `TaskPane::render` + new `TaskPane::wrapped_rows` (`src/tui/pane.rs`) — the old code took `visible_height` *unwrapped* lines, wrapped each one, and handed the result to `Paragraph`, which clips overflow at the bottom. Any line wider than the pane therefore pushed the newest output off the bottom of a pane that was supposedly following it. `render` now flat-maps the whole buffer through `wrap_line` first, asks `ScrollState::start_line` for a start *row*, and takes exactly `visible_height` rows.
- **`visible_width: Cell<u16>` alongside the existing `visible_height`** — `TaskPane` (`src/tui/pane.rs`) — the scroll offset is now in wrapped rows, so how many rows the buffer occupies depends on the width the pane last drew at. `TaskPane::total_rows()` reads that width and feeds `ScrollState::up`/`down`, which used to be handed `output_buffer.len()`; with a wrapping buffer that number was simply the wrong unit and one Up could skip a whole wrapped line's worth of output.
- **`TuiTerminal::restore` returns early when the claim is already taken** — `src/tui/mod.rs` — it used to call `claim_terminal_restore()` and discard the bool, then restore unconditionally, which is precisely the double `LeaveAlternateScreen` the claim's own doc comment (`mod.rs:33-41`) says must not happen. Phase 1's second-signal escape hatch and the panic hook both restore through `restore_terminal_best_effort`, which already honoured the claim; the guard's `Drop` was the one path that ignored it.
- **`ScrollState::bottom()` + `Pane::scroll_to_bottom()` bound to `End` and `G`** — `src/tui/pane.rs`, `src/tui/app.rs::handle_key_event` — `Home` had no counterpart, and `ScrollState::down` re-enables follow only when the user walks all the way back to the last row a line at a time, so a scrolled pane was effectively stuck on old output for the rest of the run. `bottom()` sets `follow = true` (and resets `offset`), so `start_line` tracks the newest row again. `G` is matched on `key.code` alone, so the Shift a real terminal sends with it is irrelevant.
- **The status bar names the binding in all three of its shapes** — `TuiApp::render_status_bar` — single-page, multi-page and fullscreen help lines all gained `End/G: Follow`; `examples/tui-demo/README.md` gained the key row and an Auto-Scroll line saying `End`/`G` is the one-jump way back.

### Deviations
- **The doc's first criterion says "one 3x-width line and `visible_height` rows"; the test uses one 3x-width line plus three short ones.** Same effect, stated exactly: `a_following_pane_shows_the_newest_line_even_when_a_line_wraps` (`src/tui/pane_tests.rs`) renders a 12x6 terminal (a 10x4 inner area) over a buffer of `"A"*30` plus `L1`, `L2`, `L3` — six wrapped rows for a four-row viewport — and asserts the rows are exactly `["AAAAAAAAAA", "L1", "L2", "L3"]`. A buffer of *only* one wrapping line would show its own tail either way once the window is taken in rows, so it would not pin "the newest line is visible", which is the failure the bullet describes.
- **`Pane` gained a fifth method rather than overloading `reset_scroll`.** The doc says "bind `End` and `G` to `ScrollState::bottom()`", which is not reachable from `TuiApp`: the app holds `Box<dyn Pane>`, not a `ScrollState`. `scroll_to_bottom()` is the correct seam, same effect. `StubPane` (`src/tui/layout_tests.rs`) implements it as a no-op like its siblings.

### Tradeoffs
- **Wrapping the whole buffer on every render** vs caching wrapped rows and invalidating on push/resize — the ring buffer is capped at 1000 lines and the tick rate is 10 FPS, so this is a bounded `flat_map` over borrowed `&str` slices with no allocation per row; a cache would add an invalidation rule (width change, every `push_line`, the ring-buffer eviction) whose only payoff is work that does not show up.
- **`ScrollSpy` in `src/tui/app_tests.rs` drives a real `ScrollState`** vs a "was `scroll_to_bottom` called" boolean — the doc's criterion is `follow == true`, i.e. state, not a call. A spy that records the call would pass if `End` were wired to something that happened to call the right method for the wrong reason; driving the real state means the assertion is the criterion.
- **`total_rows()` uses the last-rendered width, so a scroll keypress before the first render measures at width 0** (`wrap_line` clamps to 1, so the count is a character count). That is the same rule `visible_height` has always used and the same pre-render window: nothing is on screen yet, and `start_line` clamps the offset at the next render. Special-casing width 0 would be a second, different answer for a state the user cannot see.

## Phase 14: Dependencies and repo hygiene

### Design decisions
- **`expand_tilde()` lives in `src/executor/layout.rs`** — "where otto keeps its state on disk" already resolves `$HOME` for `resolve_otto_home()` and `xdg_data_dir()`, and `workspace.rs` already imports from it, so the new helper joins call sites that already know this module rather than creating a fourth home-directory answer somewhere new.
- **`expand_tilde()` is infallible (`PathBuf`, not `io::Result<PathBuf>`)** — a bare `~`/`~/...` that can't be expanded (no home directory found) passes the path through unchanged rather than erroring, deferring the failure to whichever caller next tries to use the path (`fs::canonicalize`, `fs::create_dir_all`). - **`~user` (someone else's home) is not expanded** — `expand_tilde` only strips a bare `~` path component (`Path::strip_prefix("~")`), which by construction never matches `~otheruser`. This is the direct consequence of dropping `expanduser`'s `pwd`/`redox_users`-backed other-user lookup for a single call on `std::env::home_dir()`, which only knows the current user.

- **`checks.yml`'s coverage-floor comment now points at `cov-report`'s own `--fail-under` comment instead of restating a number** — the number had already drifted twice (85 in the workflow comment, 87 in `.otto.yml`); restating it a second place just gives it a second place to go stale.

### Tradeoffs
- **`bin/check-doc-links` uses `grep -oP` (PCRE) for link extraction** vs. a POSIX-only pattern — this repo's CI already runs on a GNU/Linux toolchain (`checks.yml`, `ubuntu-latest`) where GNU grep's `-P` is available; a POSIX-only extraction of `](...)` would need a second pass to reject nested parens or nothing simpler than the lookaround `grep -P` already gives for free, at the cost of readability. Documented as an assumption in the script's own header via the `#!/usr/bin/env bash` + repo convention (`bin/mutants-gate` makes the same call, `set -uo pipefail` here without `-e` deliberately, so a broken link doesn't abort the loop before every miss is reported).
  - **2026-09-04 amendment: reversed. `-P` is a GNU extension, and the guard was in no gate anyway.** The tradeoff above reasons from CI running `ubuntu-latest`, and that is true of the runner but not of the developers: this repo ships macOS release artifacts and keeps a bash-3.2 job precisely because macOS is a supported surface, and BSD grep has no `-P`. Measured with a `grep` that refuses `-P` and a deliberately broken link in `README.md`: the old script printed `unrecognized option` once per file to stderr, then `✅ check-doc-links: every relative .md link resolves` and exited 0, having checked nothing. The extractor is now `grep -noE '\]\([^)]*\)'` with the delimiters peeled in the loop, byte-for-byte identical output to the `-P` version on all 78 scanned files, and a `checked` counter makes "no links found at all" a failure rather than a pass, so the same hole cannot reopen quietly. The banner now names the count. Separately, the guard ran only under `otto docs` and `otto all`, and CI runs `otto quick` and `otto cov`: the structural fix for the broken-link recurrence never ran on a PR. `.otto.yml` now has a `docs-check` leaf that runs the script alone (no `cargo doc`), and it is in `ci`'s and `quick`'s `before:` lists, so it runs in the GitHub `checks` job and in the pre-commit hook; `docs` depends on it rather than repeating the call.
  - **2026-09-05: the "no links found" guard is replaced by a check that the extractor WORKED.** The 2026-09-04 cut inferred a broken extractor from a zero link count, which is the wrong signal: it also fails a docs tree that legitimately has no relative `.md` links, and a guard that has to be deleted to get green is not a guard. grep already reports the difference in its exit status (0 matched, 1 did not match, 2 or more failed), and the old code threw it away inside the `done < <( ... )` process substitution. The extractor now runs into a variable, its status is checked, and only a real failure is fatal, per file and named: `<file>: link extraction FAILED (grep exited 2); this check is not checking anything`. Measured across the three cases that must stay distinct: a broken link exits 1 naming the link; a grep that refuses its options exits 1 with 77 failure lines and no success banner; a tree with no links at all passes with `0 relative .md links, every one resolves`. The count stays in the banner as information.
- **The guard does not follow anchors (`#fragment`) to confirm the heading actually exists** vs. a full markdown-heading-slug resolver — the doc's own bullet asks for resolving "every relative `.md` link... against the tree", which is a file-existence claim, not a heading-existence claim; a slug resolver is a meaningfully bigger and more fragile piece of code (GitHub's slug algorithm has edge cases around duplicate headings and Unicode) for a failure mode (a stale anchor into an otherwise-valid page) that is far less disruptive than a 404.
- **Archive-internal link fixes point sibling files at their real new location (`../commands/`, `../architecture/`) rather than leaving `docs/archive/` a frozen, unlinked snapshot** — the alternative (excluding `docs/archive/` from the guard, or leaving its internal links broken) was rejected under Design decisions above; the cost taken instead is nine one-line path fixes across four historical planning documents that are otherwise left as-is (their content is unedited).
